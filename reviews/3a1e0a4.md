## Findings

### 1. A slot that was unused keeps its old position when a parameter takes it later (low, CONFIRMED; residual of F5)
- **Where:** `_map_parameters_to_sliders!` (`src/MakiePlotting.jl` 161–167). The check is `get(manager.param_map, slot, param) === param && continue`.
- **What:**
  - `manager.param_map` has no entry for an unused slot, so `get` returns the new parameter and the check skips the slot.
  - Neither the new loop nor the `else` branch (unused slot) clears `slider_cache[slot]`.
  - So when a parameter is removed from the sweep, its slot keeps that parameter's position. A parameter added later in the same slot starts there, not at its first value.
  - The CHANGELOG says "A slider that shows another parameter after an edit of the sweep starts at its first value".
- **Evidence:** `p22_env.log`, sweep `(N, T)` with `T = 10` (`slider_cache[:param_2] = 10.0`):
  - Remove `T` in one edit, Run, then add `scheme` in a second edit, Run: `(:scheme, "lax_wendroff")`. The stale 10.0 snaps to index 3.
  - The same change in one edit (`T` replaced by `scheme`) gives `upwind`, which is correct.
- **Fix:** In the `else` branch (slot unused), also `delete!(manager.slider_cache, p_key); delete!(manager.pending_sliders, p_key)`.
  - Don't treat a missing old entry as "changed" instead. That would also wipe the correct position in the `set_max_params!` 1 → 2 case (p21 S3), where slots above `max_params` aren't iterated.
- **Test:** p22's two-step edit. Assert `scheme == "upwind"` after adding it.

### 2. A CSV of a 2D x–y view, loaded into an open window of a 1D setup, comes back as x–t (low, CONFIRMED; pre-existing, not caused by 3a1e0a4)
- **Where:** The bind path of `load_and_apply_csv!` into an open window. It goes through `set_sim_config!` → `_reset_config_view!`/`_reset_open_view!`, then `apply_plot_options!`, then the menu cascade at Run.
- **What:**
  - A heat CSV saved with axes `(x, y)` comes back with axes `(x, t)` and a `y` slider when it is loaded into an open advection window (`heatmap` or `lines`) and Run.
  - The same file loaded into a fresh window gives `(x, y)`.
  - The comparison, camera, animation target and `r` slider from the file are applied correctly, so 3a1e0a4's additions hold.
  - The CHANGELOG says "a CSV file applies its own [view]". The x–t CSV in p11 case 4 only passes because it matches what the menus fall back to.
- **Evidence:** `p22_env.log`, `p22_envold.log` and `p22_envfb.log` give identical results:
  - `heatplain into adv_heatmap  axes=(:x, :t) … sliders=[(:r, 0.3), (:y, 0.0)]`
  - `heatplain into fresh        axes=(:x, :y) … sliders=[(:r, 0.3), (:t, 0.0)]`
  - The same happens with `compare = time`.
- **Fix:** I did not trace the cause. A likely place: the cached `y_axis = :y` is overwritten by the menu watchers (`Watch_Plot` merges the current widget selections into `plot_cache`) before data with a `y` option arrives. One fix is to keep the CSV's plot options apart (like `pending_sliders`) and apply them after the first data of the new setup.
- **Test:** Save a heat x–y heatmap CSV, load it into an open `test_advection_1d()` window, Run, and assert axes `(x, y)`.

## Minor issues

- **F4 has no test.** Something like `@test_throws ArgumentError launch_plotter(other; style = :bogus)`, followed by a Run whose status counts the bound configuration and `isnothing(manager.launch_run)`, would pin it down.
- **Integer axes in titles (argued, not reproduced):**
  - The slider range is `range(g_min, g_max, length = 100)`, which is Float64. So the alternatives become e.g. `"Iteration = 100.000"`, while `_drawn_value` shows the dataset's Int, `"Iteration = 100"`.
  - The breaks stay stable, but they reserve more width than needed, so a title can break one line earlier than necessary.
  - A fix is to format the alternatives with the axis element type, e.g. take the ends from `_get_dim_vals` over `plot_data`, or round the slider ends when the data axis is integer.
- **CHANGELOG wording:** "it also stops a running animation, the comparison and a locked camera" reads oddly (one doesn't "stop a locked camera"). Something like "it also stops a running animation, ends the comparison and unlocks the camera" is clearer.
- **Listener cascade is clean:** after `_reset_open_view!` all three flags are set ("Run Simulation *", "Locked (Sim)"). They clear after `force_simulation()` as well as after a Run click (p20 A). `Camera_State_Sync` and `Anim_State_Change` update their buttons. The CSV path sets its own compare/camera/animation after the reset (p20 B).
- **SIGNOFF.toml:** the fb11adf annotation already covers every file 3a1e0a4 touches.

## Verdict

- Binding another setup now stops a running animation, ends the comparison and unlocks the camera, on GLMakie and headless.

What's left is small:

- Finding 2 predates this series and isn't caused by the commit, but it contradicts the "a CSV applies its own view" claim when a CSV is loaded into an open window of a 1D setup.

Neither blocks the merge. I recommend fixing finding 1 (plus a test) now, and tracking finding 2 separately.
