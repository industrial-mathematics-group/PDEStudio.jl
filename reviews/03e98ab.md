## Findings

### 1. Particle data drawn with a grid style still shows uniform display times with the nearest snapshot — medium — CONFIRMED
- **Where:** `src/DataHandler.jl:181-184` (`_load_snapshots`: `nt = raw isa ESimData && … : 0`, and `nt == 0` →
  `load_sim_data(params, Val(:eulerian), res)`), Core `convert_to_eulerian` (uniform output times, nearest snapshot).
- **What:** only native grid data gets the new stored-snapshot axis. Particle data (the native kind of particle
  solvers such as HyperCloud's) shown with a grid style keeps Core's uniform time resampling: the title and the
  reference use the display time, the drawn grid is the nearest stored snapshot — the ps-b N4 / round-1 #2 offset.
  The docstring of `_load_snapshots` says so, but `docs/src/rendering.md:46-48` ("Grid data is not interpolated in
  time: it shows its stored snapshots at their own times") and the CHANGELOG ("Grid data now shows its stored
  snapshots at their own times") state it without the exception.
- **Scenario/evidence:** `probe_particles_on_grid.jl`: particles stored at t = [0, 0.1, 0.2, 1] with u = t, Eulerian
  mode → 50 uniform display times; the slot labelled t = 0.306 holds the snapshot of t = 0.2 (offset 0.1, a tenth of
  the interval; a reference drawn with it is at 0.306).
- **Fix:** the same treatment for `LSimData` raw: `nt = length(raw.t)`; with `nt ≤ res[D]` request
  `Base.setindex(res, nt, D)` (Core's `convert_to_eulerian` keeps the native times when the slice count matches);
  with more, subsample the particle snapshots (`t`, `x`, `u`, time statistics) and convert with `length(idx)`.
  Otherwise at least name the exception in the docs and the CHANGELOG.

### 2. A re-export bundles the current original, not the code that ran — low/medium — CONFIRMED
- **Where:** `src/ConfigIO.jl` `load_and_apply_csv!` (e7c1088): `runs = [isfile(origins[i]) ? abspath(origins[i]) : bundled[i] …]`.
- **What:** `_run_bundled_sources` runs the bundled **copy** (as the original's path), but the loaded configuration's
  sources are the **originals** wherever they still exist. If the original was edited after the first export, the
  second export records the parameters that ran but bundles the edited file, so it doesn't reproduce itself.
  `_relocate_sources` already preferred originals for sources a configuration lists (pre-existing); e7c1088 extends
  that to the file that returns the configuration and to helper-only bundles, which before used the copies
  (`filter(!isempty, bundled)`).
- **Evidence:** `probe_reexport_origin.jl`: export 1 with `:version => 1`, original edited to 2, export 1 loaded
  (version 1 runs, `sources = ["…/cfg.jl"]` = the original), export 2 records version = 1 but
  `exp2_sources/cfg.jl` contains `:version => 2`.
- **Fix:** take the copies (`bundled[i]`) as the sources of a loaded export (they are what ran) and carry the
  original path separately for `source_origins`; or compare copy and original (hash, as `_load_key` does) and use the
  original only when identical. Extend the second-generation test with an edited original.

### 3. Float64 data with relative variations of 1e-13…1e-7 now fills the axis with repeated tick labels — low/medium — CONFIRMED (looked at the PNGs)
- **Where:** `src/PlottingUtils.jl` `calculate_padded_axis_range` (134a6c7, `rtol = 100 eps(precision)`).
- **What:** the N6 fix makes any Float64 variation above 2.2e-14 relative fill the axis. Makie's tick labels can't
  resolve it: at a = 1e-8…1e-13 all labels read `1×10⁰`, at 1e-7 two of five repeat. This is the round-1 #9 symptom
  (noise with repeated tick labels) back for Float64, typically in time series of conserved quantities (`mass` of a
  conservative scheme varies by round-off ~1e-14…1e-12), which before were drawn flat.
- **Evidence:** `probe_tiny_range.jl` → `tiny_range.png` (1e-13, 1e-11, 1e-9: every label `1×10⁰`),
  `tiny_range2.png` (1e-6 readable, 1e-7 partly repeated, 1e-8 all equal).
- **Fix:** keep the threshold but make the labels readable for narrow ranges (e.g. a `ytickformat` that shows enough
  significant digits or the deviation from the mid value, `1 + 2.1e-13`), or pad below a relative width Makie can
  label (~1e-7) and say so in the CHANGELOG; the user's `lims` override remains.

### 4. With the conversion cache on, every reload of data with more than 50 stored snapshots reads the whole raw data — low — CONFIRMED
- **Where:** `src/DataHandler.jl:175-189` (`_load_snapshots`).
- **What:** (a) the `nt > res[D]` path loads the full raw data and resamples on every load (each *Run*, each sweep
  point), never cached; with `enable_cache!(true)` the old path read Core's small cached conversion. (b) The stored
  count is obtained by loading the full raw data; the key includes `mtime`, which changes when Core appends a
  conversion, so the first displays of a file load the raw data twice. The CHANGELOG mentions (a) ("rather than from
  PDEStudioCore's cached conversion") but not the cost. With the cache off (the default) the new path is cheaper than
  before.
- **Evidence:** `probe_load_cost_cached.jl`, 2-D 256²×401 (200 MiB file), cache on: studio load 266 MiB / 49 ms per
  reload vs the old Core path 15.6 MiB / 2 ms; nt = 40: 217 MiB on load 1, 33 MiB on load 2 (raw re-read after the
  mtime change), 12.6 MiB after. Cache off (`probe_load_cost.jl`): 266 MiB new vs 417 MiB old.
- **Fix:** read the stored shape without loading the data (the file's `shape` entry; Core's `_native_and_shape` is
  internal, so a small public Core accessor would be cleaner) and key the count by path only, or by the file's
  `shape`; for `nt > res`, request the cached space-resampled full-time conversion
  `load_sim_data(params, :eulerian, (space…, nt))` and select from it (15 ms / 138 MiB in the probe), or document the
  cost.

### 5. `set_resolution!(:t, 1)` makes all grid data and references fail to load — low — CONFIRMED
- **Where:** `src/DataHandler.jl:187` and `:279` (`range(1, nt, length = 1)` throws "endpoints differ" for nt > 1);
  `set_resolution!` doesn't validate (the Resolution page refuses < 2).
- **Evidence:** `probe_time_display.jl` "time resolution 1 from code": "Could not load the data of …", no data.
- **Fix:** validate in `set_resolution!` (≥ 2 for a time axis, or ≥ 1) or take `idx = [nt]` when `res[D] == 1`.

### 6. `<empty>` after a Char literal `'"'` isn't replaced — low — CONFIRMED
- **Where:** `src/UILogic.jl` `_empty_literals` (464d59c) toggles the quoted state on every `"`, also inside a Char
  literal.
- **Evidence:** `probe_vector_typos.jl`: `_raw_text(Any['"', ""]) == "Any['\"', <empty>]"`, `_parse_raw` of it →
  `(false, nothing)` (the shown row can't be applied again). Niche.
- **Fix:** skip `'…'` Char literals (outside strings) in the scanner.

## Minor issues

- `_select_snapshots` keeps the raw `domain.spacing` when the space resolution already matches (`resample_eulerian`
  returns the data unchanged): spacing[t] = 2/119 instead of ≈ 2/49 in `probe_time_display.jl`. Latent (the studio
  computes no statistics on display data).
- `docs/src/rendering.md`: "the numerical curve and the reference show the same time" also fails for grid data when
  `resolution_ref[t] < resolution_base[t]` (the reference is subsampled); the docstring of `_make_reference` attributes
  this to particle data only.
- `git_dirty` is `false` for a repository whose only change is an untracked file (`probe_git_dirty.jl`), e.g. a new
  helper the configuration includes; say "changes to tracked files" in the docstring/CHANGELOG or include untracked.
- UI text options still lose surrounding spaces on reload (`" padded "` → `"padded"`, `probe_csv_spaces.jl`): the raw
  text is used only when the parsed value isn't text. Pre-existing (round-2 minor); the new test checks only `raw`.
- `_menu_label_ok` shows the value as label; for the component menu that is `"1"`, not `component_1`.
- `_csv_value_text` detects quoting by searching the whole file text; the same text quoted in another row keeps the
  spaces of an unquoted cell. Harmless.
- `manager.stored_time_counts` keeps stale `path#mtime` keys (small).

## Verdict

The round-2 fixes are careful and all come with tests that fail on the old code; the suite is green (including the
browser group). The time display redesign is correct for native grid data in 1-D/2-D with uniform or non-uniform
output, keeps time statistics consistent and invalidates its count cache correctly, and particle references now use
the data's times at a bounded cost. Remaining issues: particle data drawn on a grid still has the old time offset
and the docs overstate the fix (1), re-exports can bundle code that didn't run (2), the Float64 axis threshold trades
a flat line for unreadable tick labels on round-off-level variations (3), plus three low items.
