### Findings

#### 1. Reference solutions are laid out on the domain of the first sweep point — high — CONFIRMED
- **Where:** `src/DataHandler.jl:7-26` (`_template_data`), `:34-37`, `:167-175` (`_make_reference` uses the one
  `domain`), `:185-223` / `:420-430` (one template domain for every method and every sweep point).
- **What:** `generate_reference_simdata(ref_func, params, domain, res, mode)` gets the domain of the *first* task of
  the first numerical method for **every** grid point of the sweep. If a swept parameter changes the domain (final
  time, domain length, a grid without the end point whose extent depends on `N`, …), the reference of the other sweep
  points covers the wrong extent; `extract_eulerian_data` then picks the nearest available time/position, so the
  reference is silently drawn at the wrong time (flat extrapolation in space).
- **Scenario / evidence:** `probe_ref_domain.jl`: solver returns the *exact* transport solution `sin(x − t) + 2` for
  `T_end ∈ [1.0, 2.0]`; at `T_end = 2.0`, `t = 2.04` the numeric axis is `t ∈ [0, 2.04]`, the reference axis
  `t ∈ [0, 1.02]`; the plot (`ref_domain.png`) shows "transport" and "Analytical Solution" shifted by ≈ 1 in x
  although they are the same function. Nothing warns.
- **Fix:** build the reference per sweep point from the domain of that point's numerical dataset (e.g. take the
  domain of the dataset with the same grid index, falling back to the template), or at least cache per distinct
  domain. A test: the probe above with an assertion that reference and numeric time ranges agree per sweep point.

#### 2. Numerical and reference curves are drawn at different times; title shows a third time — medium — CONFIRMED
- **Where:** `src/PDEStudio.jl:193-198` (display resolution: time 50 for data, 100 for references),
  `src/DataHandler.jl:156` / `:170` (data resampled to `resolution_base`, references evaluated on
  `resolution_ref`), PDEStudioCore `resample_eulerian` (uniform new time axis, nearest snapshot → times relabelled),
  `src/PlottingLogic.jl:252` (time slider: 100 uniform steps), `src/DataHandler.jl:353` (nearest per dataset),
  `src/PlottingUtils.jl:107` (title prints the slider value).
- **What:** at one slider position each dataset picks its own nearest time: the numeric curve shows the original
  snapshot nearest to the nearest of 50 relabelled uniform times, the reference the nearest of 100 exact times, and
  the title the slider value. The difference is up to about one display step and can exceed the solver's time step.
- **Scenario / evidence:** `probe_time_mismatch.jl` (advection, N = 40, cfl = 0.2, solver dt = 0.0314): at slider
  t = 0.598 the upwind curve is the snapshot at t = 0.628, the exact curve is at t = 0.589, the title says
  `Time (T) = 0.598`. Max offset over all slider positions 0.039. Drawn max |upwind − exact| = 0.056, true error at the
  snapshot time 0.042 (+34 %). For a tool whose main use is comparing schemes with exact solutions this biases every
  visual error assessment (and the "compare over time" labels the same way).
- **Fix:** evaluate the reference on the time values of the numerical data actually shown (or keep the original
  snapshot times when resampling instead of relabelling to a uniform axis, and give data and references the same
  time resolution); snap the time slider to data times; print the drawn time in the title. Test: assert that the
  time of every curve equals the title's time at a few slider positions.

#### 3. Loading a CSV while other data is shown loses the saved slider positions — medium — CONFIRMED
- **Where:** `src/UILogic.jl:165-193` (`apply_slider_options!` clamps the saved value into the *current* range and
  moves the slider), `src/PlottingLogic.jl:198-200` (`_handle_slider_trigger!` overwrites `slider_cache` with the
  widget's current value before applying the new range).
- **What:** the saved value is written to `slider_cache`, but the slider is moved to the clamped value; on *Run
  Simulation* the slider step caches that clamped value over the saved one and restores it into the new range.
- **Scenario / evidence:** `probe_csv_state.jl`: export with `cfl` slider at 0.4 (sweep [0.2, 0.4, 0.5]); bind a
  configuration sweeping [0.1, 0.15] and run it; load the export: `slider_cache[:param_1] = 0.4` after the load,
  but after Run the slider is at **0.2** (range [0.2, 0.4, 0.5]). The same reload into a window showing the same
  data restores 0.4 correctly (that is what the suite covers).
- **Fix:** don't move a slider whose range doesn't contain the desired value (keep it in `slider_cache` only), or let
  `_handle_slider_trigger!` prefer a pending CSV value (e.g. a separate `pending_slider` dict consumed once).

#### 4. Reference lines add a new observer to `ax.finallimits` on every UI update — medium — CONFIRMED
- **Where:** `src/PlottingUtils.jl:136` (`lift(ax.finallimits, ax.xscale, ax.yscale)` per exponent),
  `src/PlottingLogic.jl:412-416` (delete + redraw on every `_handle_ui_trigger!`).
- **What:** `delete_plots_by_label!` deletes the line plots, but the `lift` observers stay registered on the axis
  observables. Every UI step (every slider drag frame, every *Play Anim* frame) adds one listener per exponent;
  each recomputes 100 points on every zoom/pan/limit change.
- **Evidence:** `probe_gui.jl`: with `reference = [-1.0]`, 20 UI updates raise `length(ax.finallimits.listeners)`
  from 6 to 26 while only one reference plot exists. Dragging a slider or *Play Anim* in the window adds one per
  frame (they are only dropped when the layout is rebuilt and the axis is deleted).
- **Fix:** keep the reference observables in the plot cache and update them, or `off` the lift's observer functions
  (`Observables.ObserverFunction`s from `on`/`map!`) when deleting; a regression test is the probe's assertion.

#### 5. Float32 (and SVector) parameters change type in a CSV round trip — medium — CONFIRMED
- **Where:** `src/ConfigIO.jl:31` (`add_row!` → `val2str`), `:80` (`_csv_text` only protects strings); root cause in
  PDEStudioCore `val2str` (`string(1.5f0) == "1.5"`, SVector written as `Float64[…]`).
- **What:** `:dt => 1.5f0` reads back as `1.5::Float64`, `SVector(1.0, 2.0)` as `Vector{Float64}`. The data hash
  stays the same (it is computed from the same text), so the cache silently serves the Float32 results for what is
  now a Float64 configuration; a re-run (or a solver deriving its precision from a parameter type) runs in Float64.
  The comment at `ConfigIO.jl:78-79` promises that parameters keep their type through a round trip; that holds only
  for text. Given the Float32 work downstream (HyperCloud), this matters for reproducibility of exports.
- **Evidence:** `probe_csv_roundtrip.jl` output: `f32: 1.5f0::Float32 -> 1.5::Float64`,
  `svec: [1.0, 2.0]::SVector{2, Float64} -> [1.0, 2.0]::Vector{Float64}`, `hash equal: true`.
- **Fix:** write Float32/Float16 with `repr` (`1.5f0`) and SVectors with their type in the CSV writer (or in Core's
  `val2str` if the hash change is acceptable there — it is not, so the CSV writer is the place); add these types to
  the "Simulation CSV" helpers test.

#### 6. Hand-written CSVs with spaces after the commas fail or are silently misread — medium — CONFIRMED
- **Where:** `src/ConfigIO.jl:132-138` (`_read_csv`: header names and `Category`/`Scope`/`Parameter` cells are used
  verbatim).
- **What:** the docs (`docs/src/presets.md:14, 55`) say the files "can be written by hand" and describe every row as
  `Category, Scope, Parameter, Value`. A header written like that gives `KeyError: key :Scope not found`; rows like
  `Simulation, Shared, N, 40` give scope `" Shared"` and key `" N"`, which `csv_to_simulation_config` treats as a
  **method named " Shared"** with a parameter `" N"` — no error, the shared `N` is unchanged.
- **Evidence:** `probe_csv_roundtrip.jl`, testset "Hand-written CSV": `KeyError: key :Scope not found`, and
  `Dict("Simulation" => Dict(" Shared" => Dict(" N" => 40)))`.
- **Fix:** `CSV.Rows(filepath; stripwhitespace = true)` (or `strip` the three key cells and normalise header names);
  warn on unknown categories / scopes.

#### 7. A bundled `.jl` config that ends with a function is not used on reload — medium — CONFIRMED
- **Where:** `src/ConfigIO.jl:268, 281` (`_run_bundled_sources` takes the include result only if it `isa
  SimulationConfig`), compare `:326-327` (`load_config_file!` also accepts a function and calls it).
- **What:** `load_config_file!` documents and supports "a function without arguments that returns" the config; the
  export bundles that file. On reload the function is not called, so the parameters come from the CSV, where
  function-valued parameters (initial conditions, flux functions, …) are the string `"Closure"`. No failure is
  reported (`source_failures` empty, status line silent); the next *Run* passes `"Closure"` to the solver.
- **Evidence:** `probe_bundled.jl`: `cfgsrc/myconfig.jl` ends with `probe_cfg` (a function returning a config with
  `:ic => initial_condition`); after export + reload `shared[:ic] = "Closure"::String`, `source failures: String[]`.
- **Fix:** in `_run_bundled_sources`, `last_result isa Function && (last_result = Base.invokelatest(last_result))`
  as in `load_config_file!`; more generally warn when a CSV-sourced configuration contains `"Closure"` values.

#### 8. Default display/reference resolutions make 3-D data infeasible — medium — SUSPECTED (arithmetic, not run)
- **Where:** `src/PDEStudio.jl:193-198` (200 / 400 points per spatial dimension, 50 / 100 in time),
  `src/DataHandler.jl:156, 170`.
- **What:** resolutions are per-dimension constants, so the memory per dataset grows like 200^D. For 3-D + time data
  every dataset is resampled to 200×200×200×50 = 4·10⁸ values (3.2 GB per component, per method, per sweep point)
  and every reference is evaluated on 400×400×400×100 = 6.4·10⁹ points (51 GB per component) — the container's
  32 GB limit kills the process at the first *Run* of a 3-D configuration with a reference. Even 8³ data is upsampled
  to 200³. No test uses real 3-D spatial data (the "3D" tests are x × t × cfl). I did not run it to avoid an OOM
  kill on the shared machine.
- **Fix:** cap the total number of display points (e.g. scale the per-dimension default with D), never upsample
  beyond the data's own resolution, and evaluate references only on the slice being shown.

#### 9. 1-D axis limits blow up Float32 round-off — low — CONFIRMED
- **Where:** `src/PlottingUtils.jl:499-515` (`calculate_padded_axis_range`: `data_range ≈ 0` is only true for an
  exactly zero range).
- **What:** the colour-range path got a relative floor (`_pad_degenerate_range`), the axis-limit path didn't: a field
  that is constant up to Float32 noise (initial states, conserved quantities over time) fills the whole y axis with
  noise and gets repeated tick labels.
- **Evidence:** `probe_axis_limits.jl` + `axis_limits_const.png`: limits 1.39999985 … 1.40000010 (width 2.5e-7),
  tick labels "1.4000000×10⁰" and "1.3999999×10⁰" twice each.
- **Fix:** reuse `_pad_degenerate_range` for the axis limits.

#### 10. PDEStudioCore compat admits versions without the documented quick start — low — CONFIRMED
- **Where:** `Project.toml` `[compat] PDEStudioCore = "0.4"`; `README.md:44-57`, `docs/src/index.md:83-103`,
  `src/MakiePlotting.jl:286, 326-329` use `test_advection_1d()` etc., exported only from PDEStudioCore 0.4.3.
- **What:** with Core 0.4.0–0.4.2 (the local `test/Manifest.toml` resolves 0.4.0) the README's first command fails
  with `UndefVarError`, and the suite only `@test_skip`s the built-in examples (the "Broken" in the run above), so CI
  with an older resolved Core would not notice.
- **Fix:** propose `PDEStudioCore = "0.4.3"` (a compat change: user's decision); make the skip a failure when the
  Core version satisfies the compat lower bound.

#### 11. Style values the editor accepts can't be drawn — low — CONFIRMED
- **Where:** `src/UILogic.jl:890` (`_valid_ui_value`: `_valid_color([]) == true`, no checks for `color_range`,
  `levels`), `src/Render.jl:127, 156, 259` (`mod1(m_idx, 0)`, `range(…, length = levels)`),
  `src/PlottingUtils.jl:192` (`cr_val[2]`).
- **Evidence:** `probe_style_values.jl`: `colors = []` → `DivideError`, `color_range = [1.0]` → `BoundsError`,
  `levels = 1` with `contour_f` → `ArgumentError` (`apply_ui_style!` uses `max(2, levels)`, the initializer
  doesn't). The plot step catches them and logs "Updating the plot failed …", so the studio stays usable, but the
  editor reported the change as accepted.
- **Fix:** validate non-empty `colors`/`markers`/`line_styles`, a 0- or 2-element `color_range` and `levels ≥ 2` in
  `_valid_ui_value`; use `max(2, levels)` in `initialize_base_plot!(::Val{:contour_f})`.

#### 12. Provenance records miss the sub-dependencies of local repos — low — CONFIRMED
- **Where:** `src/ConfigIO.jl:657-668` (`pkg.name in git_repo_names`), `:728` (`get_all_git_infos(pwd())`).
- **What:** repository folders are named `<Name>.jl`, packages `<Name>`, so the comparison never matches and the
  "sub-dependencies of tracked local Git repositories" (docstring `:640-641`) are never written. Repos are also
  searched only below the working directory, not where the loaded (dev'd) packages live, and the dirty state of a
  repo is not recorded.
- **Evidence:** from `/workspace/julia/PDEStudioDev`: git repos `["PDEStudioCore.jl", "PDEStudio.jl"]`, Julia scopes
  `["Main_Project", "System"]` although PDEStudio is a dependency of the environment.
- **Fix:** strip a `.jl` suffix (or compare with `pkg.source` paths), add repos of dev'd packages from
  `Pkg.dependencies()` (`pkg.source`), record `LibGit2.isdirty`.

### Test coverage

Well tested: the reactive cascade end to end (every Eulerian style is built through real widget clicks), compare
modes, static and animated exports, the CSV pipeline (export → load → run, backend keys), visual and simulation
preset round trips, `.jl` configs and bundled sources (very thorough, including missing originals and uploads),
non-numeric sweeps, the launcher and the mode switch, colour-range padding and colour validation. The suite passes
reliably and fast (parallel groups).

Gaps:
- **No test checks the drawn values.** The base-style loop asserts `active_plot_type` and that a primitive exists in
  the cache; a plot step that throws after `initialize_base_plot!` (errors are caught and only logged) or draws the
  wrong slice would still pass. Worth adopting: the `lines_1d` value check in `probe_gui.jl` (drawn `obs_u` equals the
  dataset at the selected `cfl`/`t`; currently exact) and a `@test_logs` / no-`:error` guard around the style loop.
- **References vs numerical data:** nothing tests that a reference is drawn at the same time / on the same domain as
  the data. `probe_ref_domain.jl` and `probe_time_mismatch.jl` are ready-made regression tests for findings 1 and 2.
- **CSV round trips** cover a handful of keys. `probe_csv_roundtrip.jl` (value-type table, hand-written file) and
  `probe_csv_state.jl` (slider restore across different data) are worth adopting; the bundled-function case
  (`probe_bundled.jl`) too.
- Observer leaks: the listener count assertion from `probe_gui.jl` (finding 4).
- Float32 data and real 3-D spatial data (x, y, z, t) are not exercised anywhere in the suite.
- Lagrangian rendering is only checked for `scatter_1d`; 2-D/3-D particle styles and their sync path are covered
  only indirectly by the mode-switch tests.

### Verdict

The area is in good shape structurally: the tiered lock design is consistent, the CSV format is careful about text
values and never evaluates code, and the suite is broad and green (and green against Core 0.4.3 too). The serious
problems are in what the plots claim: references are laid out on the first sweep point's domain (finding 1, high:
visibly wrong overlays for sweeps over final time or domain size) and are drawn at a different time than the data
and the title (finding 2), which together undermine the main use case of comparing schemes with exact solutions.
On the IO side, Float32/SVector parameters, function parameters from bundled function-style configs and
hand-written files with spaces don't round-trip (findings 5–7), and CSV slider positions are lost when loaded over
other data (finding 3). The tests never check drawn values, which is why these pass unnoticed.
