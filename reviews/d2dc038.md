### Findings

#### N1. A failed export leaves the export figure's render listeners attached; NaN/Inf frame rates are accepted — low/medium, CONFIRMED
- **Where:** `src/UILogic.jl:2260–2342` (`Export_Click`): the export figure's listeners (`export_obs`, from
  `setup_render_lift!`) are only switched off at line 2323, inside the `try`; the `catch`/`finally` don't. Lines
  2277–2278 convert `animation_time` / `animation_FPS` unchecked (`round(Int, NaN)` throws), and
  `_invalid_ui_reason` (`UILogic.jl:924–934`) doesn't validate the export settings, so `NaN`/`Inf` can be typed in
  *Files → Settings ›*. The round-1 fix (5) validates only *Play Anim* (`UILogic.jl:2375`).
- **Scenario:** type `NaN` into `animation_FPS` (accepted: "Export settings → animation_FPS = NaN"), select an
  animation target, export `x.mp4` → "Export failed: InexactError: Int64(NaN)". Afterwards `triggers[:Plot]`,
  `[:Slider]`, `[:PlotData]`, `[:UI]` each have 2 listeners instead of 1; after a second failed export 3. Every
  later plot update, slider drag frame and UI update also re-renders into the hidden export figure. The same
  holds for any failure after the export figure was built (CairoMakie save error, unwritable folder, ffmpeg error).
  The main window stays correct in the probe (its listener runs last), so the effect is growing wasted work per
  failed export and any errors the stale handlers log.
- **Evidence:** `probe_a1.jl` "N1"/"N1b" (`bad = Dict(:Plot => 2, …)` vs `base = … => 1`; NaN stored),
  `probe_a2b.jl` ("listeners after 2 failed exports = 3"; main plot still updates).
- **Fix:** off the export listeners in `finally` (`isnothing(export_obs) || foreach(off, export_obs)`), and validate
  `animation_FPS`/`animation_time` (finite, > 0) both before the export and in `_invalid_ui_reason` (also `dpi`).

- **Where:** `src/Presets.jl:76–81` (`_preset_rows` reads `CSV.Rows(path)` and `getproperty(row, :Scope)`, i.e. the raw
  header names), called from `_editor_scope_valid` / `_render_editor!` (`UILogic.jl:1226`, `1660`);

### Findings

#### N1. Exporting a reloaded export drops its bundled sources (function parameters become `"Closure"`) — medium — CONFIRMED
- **Where:** `src/ConfigIO.jl:416-417` (`sources = … _relocate_sources(bundled_config.sources, bundled, origins)`),
  `:508` (`isempty(sources) || (config.sources = sources)`), `:267-320` (`_run_bundled_sources`).
- **What:** when a bundled source returns a configuration, the loaded configuration's `sources` are taken from that
  configuration's own `sources` field. A config file doesn't list itself (`load_config_file!` adds the file at
  `:368`, `_run_bundled_sources` doesn't), so `sources` ends up empty. Saving the loaded state writes no
  `bundled_sources`; loading *that* export gives `:ic => "Closure"` (and, since `val2str` of a function is also
  `"Closure"`, the same data hash: cached results load, a re-run passes a string to the solver).
- **Regression of the finding-7 fix:** before `330766b`, a file ending with a *function* gave `bundled_config ===
  nothing`, so the bundled copies were kept as sources. Calling the function now takes the other branch. Files ending
  with a `SimulationConfig` had this bug before as well.
- **Evidence:** `probe_reexport.jl`: after reload `active_config.sources = String[]`, second export
  `bundled_sources = nothing`, reloaded `typeof(shared[:ic]) = String` (both file kinds). With the pre-`330766b`
  `ConfigIO.jl` the function case keeps `["exp2_sources/fn_cfg.jl"]`.
- **Fix:** do what `load_config_file!` does: add the bundled copies (or at least the file that returned the config)
  to the config's sources, e.g. `sources = unique([_relocate_sources(…); filter(!isempty, bundled)])`. The
  "Bundled config file ending with a function" test should save and reload a second time.

#### N2. Style values from CSV files and visual presets are not validated — low/medium — CONFIRMED

  crash sites `src/PlottingUtils.jl:203` (`cr_val[2]`), `src/Render.jl:127-128` (`mod1(m_idx, end)` on an empty
  list; also `src/PlottingLogic.jl:452`);
  `src/MakiePlotting.jl:571-575` (the UI step has no `try`, unlike the plot step).
- **What:** round-1 finding 11 was fixed in the editor only (`_invalid_ui_reason` at `src/UILogic.jl:924` is called
  only by the editor commit, `:1911`). A visual preset or hand-written CSV with the same values still breaks the
  plots. CHANGELOG says such values "are refused now", which is only true for the editor.
- **Evidence:** `probe_gui.jl` (PROBE=style): `UI,plot_style,color_range,"[1.0]"` → stored `[1.0]`, then
  *Apply Layout* throws `BoundsError: attempt to access 1-element Vector{Float64} at index [2]` out of the UI step
  into the click handler; `colors = Any[]` / `line_styles = Any[]` → stored, every plot update logs "Updating the

#### N3. Lagrangian references: non-uniform stored times are not honoured, and the cost now grows with the stored times — medium — CONFIRMED
- **Where:** `src/DataHandler.jl:206-225` (`_make_reference`: only the Eulerian branch handles a non-uniform
  `t_axis`; for `Val(:lagrangian)` it sets `res[D] = length(t_axis)` and Core lays out uniform times).
- **What (a):** the docstring (`:198-205`) and `docs/src/rendering.md` promise the reference is evaluated at exactly
  the data's times. For particle data stored at non-uniform times (adaptive steps, output at chosen times) it is
  evaluated at `length(t)` uniform times instead, so the reference shows a different time than the numerical data.
  This is worse than before the fix: the old 100-point uniform grid was at most 0.005·T away; now the offset can be
  a large part of the interval.
- **What (b):** the time count of a Lagrangian reference was capped at `resolution_ref[:t] = 100`; it is now the
  number of stored times of the data, times `resolution_ref` particles (400² in 2-D). Raw particle data (and
  Eulerian data shown with a particle style, which is not resampled in time) often has hundreds to thousands of
  stored times, so one reference per sweep point (and per distinct domain) reaches GBs.
- **Evidence:** `probe_lag_ref_times.jl`: data `t = [0, 0.1, 0.2, 1]` → reference `t = [0, 0.333, 0.667, 1]`; at
  slider 0.2 the data is drawn at 0.2, the reference at 0.333. `probe_lag_ref_cost.jl` (2-D, 160 000 reference
  particles): 201 stored times → 248 MiB, 1001 → 1.2 GiB allocated per reference (before: ~120 MiB for any data).
- **Fix:** for Lagrangian data build the reference like `_reference_on_axes` with `t_vec = t_axis` (Core's
  `_reference_particles` takes a `t_vec`), and cap or subsample the time count (e.g. evaluate only the times the
  slider can reach, or lazily per drawn snapshot).

#### N4. The remaining time offset of the drawn reference is up to half the *stored-snapshot interval*, not "half a solver step" — medium — CONFIRMED
- **Where:** `docs/src/rendering.md:43-49`; `src/DataHandler.jl:153-158` (display data resampled in time with
  `resolution_base[:t]`), `:198-205` (docstring: "show the same time").
- **What:** after the fix the reference is evaluated at the *display* times of the resampled data, while the numerical
  curve shows the stored snapshot nearest to that display time (Core relabels it). The offset is up to half the
  interval between *stored* snapshots: solvers that store every k-th step, or store fewer snapshots than the display
  resolution (upsampling in time with nearest-neighbour), get offsets of many solver steps, and the title shows the
  display time, not the drawn snapshot's. The doc's bound "at most half a solver step" is wrong in these cases, and
  "the numerical curve and the reference show the same snapshot" is not what happens.
- **Evidence:** `probe_time_offset.jl`: numerical data *is* the exact solution `sin(x − t) + 2`, dt = 0.01, stored
  every k steps: max |display time − snapshot time| = 0.0049 / 0.0196 / 0.098 and drawn |numeric − reference| up to
  0.005 / 0.020 / **0.098** (10 % of the amplitude, for two identical solutions) for k = 1 / 4 / 20. Even k = 4
  (51 stored times → 50 display times) gives 0.02.
- **Fix:** this can be done in PDEStudio without waiting for Core: don't resample the time axis for display (request
  the stored time count in `build_res_tuple`'s time entry, e.g. from the template data or `_native_and_shape`, capped
  at a maximum), so display times are real snapshot times; or at least never upsample in time. Then correct the doc
  (the bound is half the stored-snapshot interval) and the docstring.

#### N5. CSV round trip: other numeric and container types still change type — low — CONFIRMED
- **Where:** `src/ConfigIO.jl:86-100` (`_needs_type` covers Float32/Float16/SVector only).
- **What:** `Int32(3)` → `3::Int64`, `UInt8` → `Int64`, `MVector` → `Vector`, `SMatrix` → `Matrix`, `0.0:0.5:1.0`
  → `Vector`, a `NamedTuple` → the string `"NamedTuple(a=1, b=2.0)"`, and `missing` → the **type** `Missing`
  (`val2str(missing) == "Missing"`, read back as a type). The hash stays the same in all cases, so the cache hides
  the change until a re-run. `Int32` parameters are plausible for the GPU/Float32 work downstream.
- **Evidence:** `probe_csv_values.jl` (38 kinds; the 7 above fail, the hash is equal).
- **Fix:** write non-default integer types with their constructor (`Int32(3)`, which `str2val` reads), `missing`
  as `missing` (a `_LITERAL_CONSTANTS` entry), and `MVector`/`SMatrix` like `SVector` (or warn that they come back
  as plain arrays); extend the helpers test table.

#### N6. Axis limits hide small relative variations of Float64 data — low — CONFIRMED
- **Where:** `src/PlottingUtils.jl:185-190` (`_pad_degenerate_range`: relative 1e-5 threshold), `:522-526`
  (now also used for 1-D axis limits, round-1 finding 9).
- **What:** the threshold suits Float32 round-off but treats any relative variation below 1e-5 as "constant" and
  widens the axis to ±1e-3 relative. A Float64 perturbation of relative amplitude 1e-6 (linear acoustics,
  perturbation tests) is drawn as a flat line; before the fix the axis showed it. The colour range already behaved
  so (it is Float32, so it can't resolve much below 1e-7 anyway), but Makie's axes handle such offsets.
- **Evidence:** `probe_small_perturbation.jl`: `u = 1 + a sin(x)`: a = 1e-5 spans 91 % of the axis, a = 1e-6
  0.1 %, a = 1e-8 0.001 %.
- **Fix:** use an absolute/relative threshold tied to the data's precision (the drawn data's `T`, e.g.
  `100 eps(T)`), or make the padding of degenerate ranges an axis option; the user can set `lims` by hand meanwhile.

#### N7. A CSV slider position outside its data's range stays pending and overrides later user positions — low — CONFIRMED
- **Where:** `src/UILogic.jl:199` (`pending_sliders` set), `src/PlottingLogic.jl:207-235` (consumed only when a
  range changes or contains it), `src/MakiePlotting.jl:538-553` (a drag doesn't clear it).
- **What:** if the saved position is outside the range of the data the file brings (hand-edited value, data re-run
  with another final time), the entry is never consumed while that data is shown. The user moves the slider, later
  runs any configuration with another range, and the slider jumps to the stale file value.
- **Evidence:** `probe_gui.jl` (PROBE=pending): `Scene,Plot,t,5.0` loaded over t ∈ [0, 2.01] → pending `t => 5.0`;
  slider dragged to 0.5; *Run* with N = 50 → slider at 2.01 (the clamped 5.0), not 0.5.
- **Fix:** drop the pending entry when the user moves the slider, or consume it at the first slider step after the
  file's own data is loaded (clamped).

#### N8. Hand-written CSV: labels keep the space after the comma — low — CONFIRMED
- **Where:** `src/ConfigIO.jl:164` (`val_str` kept unstripped), `:566` (labels use the raw text).
- **What:** `Scene, Labels, upwind, Upwind scheme` gives the label `" Upwind scheme"` (legend, menus); the same
  text as a UI option is stripped by `str2val`. Round-1 finding 6 (spaces after commas) is fixed for keys only.
- **Evidence:** `probe_handwritten_text.jl`.
- **Fix:** strip unquoted raw values (CSV.jl removes the quotes, so keep the raw text only for quoted cells, or
  `lstrip` one separator space).

### Minor issues

- `src/DataHandler.jl:176-178, 216-217`: `_reference_on_axes` keeps the numerical data's `domain.spacing`
  (`_with_time_bounds` copies it), while the reference has `resolution_ref` points (Core's own path recomputes it).
  `spacing` is the integration measure of statistics, so any statistic computed on such a reference would be off
  by the resolution ratio. Latent today (the studio doesn't compute statistics on references). The loop is also
  serial where Core's version is threaded.
- `src/ConfigIO.jl:745-746`: the `save_params_to_csv` docstring still says the sources are copied as
  `<name>_source_<i>.jl`; they go to `<name>_sources/<file>`.
- `src/DataHandler.jl:273`: `numeric` from a previously bound configuration with the same sweep shape and key names
  is accepted (only size and keys are compared), so a reference created by a layout step between binding a new
  config and *Run* is laid out on the old data's domain; the next *Run* (`force_reload`) replaces it. Transient.
- `src/ConfigIO.jl:211-217` + `str2val`: UI text options lose surrounding spaces and quotes on reload (`"  padded  "`
  → `"padded"`, `"\"q\""` → `"q"`); the raw text is used only when the parsed value isn't text.
- `src/PlottingUtils.jl:170`: the reference-line fix relies on `getfield(l, :deregister_callbacks)`, a Makie
  internal; keeping the reference lines in the plot cache and updating them would avoid both the leak and the

### Verdict

The round-1 fixes in this area are mostly sound and each comes with a regression test that fails on the old code;
the CSV reader is now robust against hand-written files, and the reference/domain fix (finding 1) is correct. Three
fixes are incomplete or have side effects that matter: re-exporting a reloaded export loses its bundled code (N1,
partly a regression of the finding-7 fix), style values are validated only in the editor (N2), and the
"reference at the data's times" work holds for the display labels of Eulerian data only: Lagrangian data with
non-uniform times got worse and the reference cost is no longer bounded (N3), while for sparsely stored Eulerian
output the drawn reference is still up to half a stored interval off, contrary to the documentation (N4). The
remaining items are low (type coverage of the CSV writer, small Float64 variations flattened, a stale pending
slider, label whitespace). Full suite green (681 pass, 1 skip from the local Core 0.4.0; the examples pass with
Core 0.4.3).
