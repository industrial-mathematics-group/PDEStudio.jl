## Findings

### 1. `studio_snapshot` throws on a GLMakie window for `heatmap_surface`. High, CONFIRMED.
- **Where:** `studio_snapshot`, `src/AgentAPI.jl:294`: `Makie.colorbuffer(fig; backend = CairoMakie, …)` renders the live figure.
- **What:** If the open window is GLMakie and the style is `heatmap_surface`, every snapshot fails with `ErrorException: Cannot register computation: Some outputs already have parent compute edges: positions_transformed`. This also happens with `area = :window` and on retries. GLMakie windows and 3D views are central to the owner's request.
  - The other 3D styles render (lines_3d, scatter_3d, contour_3d, contour_surface); volume renders blank (F2).
  - Headless CairoMakie and WGLMakie without a browser are not affected (p01, p09).
  - In `p07`, a volume snapshot taken later in the same session came out cropped to the control panel (`p07_gl_volume_snapshot.png`). A fresh session crops correctly (`p08_volume_3d_a.png`). That this is damage left by the failed render is PLAUSIBLE, not proven.
- **Evidence:** `p07.log`, `p08_gl3d.jl` (three attempts), `p13.log`.
- **Fix:** Don't render the live figure with a second backend.
  - If the current screen can render (GLMakie under Xvfb), use `Makie.colorbuffer(fig)` with its own backend, then crop. This also shows volumes.
  - Otherwise render a copy, as the export path already does (`_setup_export_interactions!` builds a separate figure).
  - Keep CairoMakie for headless use and for WGLMakie without a browser.
- **Test:** In `plots-2`, snapshot `heatmap_surface` (and volume) on the GLMakie window. The current GLMakie test only covers `lines_1d`.

### 2. Volume plots come out blank in every snapshot. Medium, CONFIRMED.
- **Where:** `studio_snapshot` (always CairoMakie); the docstrings and `docs/src/agents.md` ("snapshots are still rendered by CairoMakie").
- **What:** CairoMakie can't draw `volume`: it only logs `Makie.Volume… is not supported by cairo right now`. A `volume_3d` snapshot shows an empty 3D box with a colorbar, headless and also with a GLMakie window that draws the volume (`p07_gl_volume_native.png` vs `p08_volume_3d_win.png`). Nothing in the return value, the status or the docs tells the agent, so it may conclude the data is empty.
- **Evidence:** `p04_volume_rot.png`, `p08_volume_3d_a.png`, `p08_volume_3d_win.png`, `p07_gl_volume_native.png`.
- **Fix:** Use the window's own backend (F1). Headless, warn: put a `:warn` status or a field in the return value, and say in the docs that volumes can't be rendered without GLMakie.
- **Test:** A volume snapshot is not uniform inside the axis (GLMakie), or a warning is reported (headless).

### 3. The automatic camera lock keeps old limits after the plotted variables change. Medium, CONFIRMED.
- **Where:** `_lock_view!` (`src/AgentAPI.jl:81`), used by every camera function; `_enforce_camera_lock!` re-applies limits by subplot index.
- **What:** After any `studio_zoom!`, `studio_pan!` or `studio_view!`, the camera stays locked. A later `studio_set!(:x_axis => :t)` keeps the x limits of the old variable, so the plot is empty: x ∈ [0.176, 0.424] of *time*, y ∈ [0.24, 0.76]. The axis limits (`lims`) set on the UI tab are also ignored silently while locked (`apply_axis_limits_overrides!` returns early).
  - The Lock Camera button behaves the same, but a person turns it on knowingly. Here every zoom turns it on, and an agent doesn't see the result until it takes a snapshot.
  - The docs promise the view stays "while sliders move and the data updates", which also covers axis, style and compare changes, where keeping the limits is rarely wanted.
- **Evidence:** `p02.log` (section A), `p02_xaxis_t_locked.png` (empty axes with legend).
- **Fix:** Store what the view belongs to (style and x/y/z/u/component, compare) when the API locks. Release the lock, or reset the view, when `studio_set!` changes any of these. At minimum, document it and say "camera locked" in the `studio_set!` status.
- **Test:** Zoom, then `studio_set!(:x_axis => :t)`; expect the x limits to cover the t range and `camera_locked == false`.

### 4. Failed redraws are reported as success; `studio_option!` accepts values the UI tab rejects. Medium, CONFIRMED.
- **Where:**
  - `studio_option!` (`src/AgentAPI.jl:765–777`) checks only `_invalid_ui_reason`, then always sets an `:ok` status.
  - The render catch blocks (`MakiePlotting.jl:517`, `:583`) only write `@error` to the log.
- **What:** The tab's `_apply_editor_input!` keeps text options as text and rejects text for numbers and booleans (`_valid_editor_value`). The API doesn't, although its docstring says "checked like the tab's input". These calls redraw with an exception, and `studio_state().status` reports `level = :ok`:
  - `studio_option!(:labels, :title, 5)`
  - `studio_option!(:y_axis_1d, :log_scale, "yes")`
  - `studio_option!(:y_axis_1d, :padding, "a")`
  - `studio_option!(:plot_style, :line_width, :thick)`

  `studio_set!` has the same blind spot: if the render step fails, the status still says "Set … (apply_layout)." with `:ok`. An agent that relies on the status (as the docs advise) can't tell the plot failed.
- **Evidence:** `p02.log` (`title = 5` stack trace, then status "Plot → title = 5"), `p03.log` section 5.
- **Fix:**
  - Apply the tab's checks: the type of the old value, `_valid_editor_value`, `_invalid_ui_reason`.
  - Have the render catch blocks set an `:error` status, or a `manager.last_render_error` that the API reads.
  - Don't overwrite a `:warn` or `:error` status in `studio_option!`. `studio_set!` already checks whether the status changed.
- **Test:** `@test_throws ArgumentError studio_option!(:labels, :title, 5)` and the same for `:log_scale => "yes"`. Then force a render failure and check `studio_state().status.level !== :ok`.

### 5. Non-numeric sweeps report the slider index as `value`. Low–medium, CONFIRMED.
- **Where:** `_slider_state` (`value = sl.value[]`), `studio_controls`, and the `values` returned by `studio_set!`.
- **What:** For `:scheme => ["upwind", "lax_friedrichs", "lax_wendroff"]`, the control is `value = 1, choices = ["upwind", …]`, and `studio_set!(:scheme => "lax_wendroff")` returns `values[:scheme] = 3`. Passing a value read back from the API to `studio_set!` fails: `studio_set!(:scheme => 2)` gives "slider :scheme has no value 2". `describe_studio` prints `scheme [slider] = 2  ("upwind", …)`.
- **Evidence:** `p04.log` section 1.
- **Fix:** Report the swept value (`vals[Int(value)]`) as `value` for non-numeric sweeps, or also accept an index in `_set_slider_control!`.
- **Test:** For every slider, `studio_set!(c.name => c.value)` round-trips; for text sweeps, `value isa String`.

### 6. Subplot snapshots (`plot = i`) leave out the subplot's own colorbar and include parts of neighbours. Low, CONFIRMED.
- **Where:** `studio_snapshot`, `_union_box(_axis_box(ax), _drawn_box(ax))`.
- **What:** With `compare_link = :decoupled` (one colorbar per subplot), `plot = 1` cuts the colorbar to a sliver, so the colours can't be read. In coupled grids, tick labels of the neighbour on the left ("0") and a sliver of the shared colorbar appear at the edges.
- **Evidence:** `p04_decoupled_p1.png`, `p01_compare_p2.png`, `p01_compare_p3_2x.png`.
- **Fix:** Add the subplot's colorbar or legend (they sit next to it in the grid layout) to the box. Clip to the subplot's grid cell, not a fixed 6 px margin.
- **Test:** In a decoupled heatmap compare, the `plot = 1` snapshot is wider than its axis box by about the colorbar width.

### 7. `studio_zoom!(dims = :z)` on 2D plots does nothing but locks the camera. Low, CONFIRMED.
- **Where:** `studio_zoom!` and `_zoom_dims`.
- **What:** `zlims` and `dz` throw on 2D plots, but `dims = :z` returns unchanged limits, sets `camera_locked = true` and reports "Zoomed in ×2".
- **Evidence:** `p03.log` section 1.
- **Fix:** Throw if none of the selected plots has a selected axis direction.
- **Test:** `@test_throws ArgumentError studio_zoom!(2; dims = :z)` on a 2D plot.

### 8. `studio_reset_view!` relies on the PlotData pass to recompute 2D limits. Low, CONFIRMED (edge case).
- **Where:** `src/AgentAPI.jl:240–253`.
- **What:** For 2D axes the reset only increments `triggers[:PlotData]`. If that pass sets no limits, the zoom stays. Example: only the `exact` method active, automatic view (0, 10), zoom to (3.75, 6.25), and reset keeps (3.75, 6.25), also after a `t` change.
- **Evidence:** `p03.log` section 3.
- **Fix:** Call `autolimits!(ax)` (or `ax.limits[] = (nothing, nothing)`) for 2D axes before the trigger.

### 9. Swept parameters beyond `max_params` are listed but can't be set, and nothing says so. Low, CONFIRMED.
- **What:** With three swept parameters (default `max_params = 2`), `describe_studio` lists `swept cfl = 0.25, 0.5` but shows no slider. The plot uses the first value, and `studio_set!(:cfl => 0.5)` gives "no control named :cfl" without mentioning `set_max_params!`.
- **Evidence:** `p10.log`.
- **Fix:** Mark such parameters as pinned (`cfl = 0.25 (no slider; set_max_params!(3))`) and add that to the error message.

### 10. Non-PNG paths fail with an obscure error. Low, CONFIRMED.
- **What:** `studio_snapshot("x.jpg")` throws a `CapturedException` (an `ARGB32` TypeError, ImageMagick/OpenCV missing). The docstring says PNG.
- **Evidence:** `p02.log`.
- **Fix:** Check the `.png` extension and throw an `ArgumentError`.

## Minor issues

- **Azimuth not wrapped:** the reported azimuth grows without bound (525° after four 120° turns; `p12.log`). Report `mod(az, 360)`.
- **`plot = true`:** gives "invalid index: true of type Bool" because `Bool <: Integer`.
- **Partial changes:** `studio_view!`, `studio_zoom!` and `studio_pan!` apply limits axis by axis, so a validation error on a later subplot leaves earlier ones changed and unlocked. Validate all axes first.
- **Which method a heatmap shows:** a single-method style (heatmap) shows one method (`value_ranges` has only `:explicit`). `describe_studio` doesn't say which, or that `studio_option!(:plot_style, :method_index, …)` chooses it.
- **Title cut off in snapshots:** the plot-area snapshot cuts long titles at the control panel edge (by design, `_controls_right`). With the default 1259 px window the time value at the end of the title is cut off on the right too; this overflow already exists in the window. `studio_state()` has the full title.
- **Pre-existing state leak, not from this change:** `launch_plotter(new_config)` after `reset_plotter!` inherits menu and slider state from the previous config (y axis `:t`, r = 0.3, empty plot), also without any API call (`p06_leak.jl`). It matters for agents that relaunch with different configs and is worth a separate issue.
- **3D compare subplots aren't linked:** they never are in the window either. "linked subplots move together" in the docs is correct but could say "2D".
- **Window not required everywhere:** `studio_options()` works without a window while the other functions throw. This is harmless, but undocumented.
- **No API for some buttons:** Play Anim, Export and presets have no API; existing functions cover presets, and `t` can be stepped instead of playing.
- **Snapshot file names:** two default snapshots within the same millisecond would overwrite each other.
- **Test runner change is fine:** `runtests.jl` replaces `addenv` with `setenv(Dict(ENV) …)` and loads GLMakie conditionally. Parallel, single-process and agent-only runs all pass; the agent child really runs without DISPLAY.
- **No GUI behaviour change found:** the API only adds code. The camera-cache keys and the status line are shared with the lock button, and that works both ways (`p02`/`p03` section E/4: unlocking with the button and then updating the data rescales).
- **SIGNOFF.toml:** the block follows the existing convention. It declares A2, so it depends on this review being committed under `reviews/`.

## Verdict

Changes needed before merging. The API covers what was asked: state, controls, sliders, menus, styles, methods, options and 2D/3D camera work without a display, errors for wrong names or values list the valid ones, the existing suite passes (parallel and single process), and the docs build cleanly. But the snapshot path fails for a main 3D style on GLMakie (F1) and shows nothing for volumes (F2). Together with the stale locked view (F3) and redraw failures reported as success (F4), an agent can be misled about what is plotted.

Counts: 1 high (F1), 3 medium (F2, F3, F4), 6 low (F5–F10), 11 minor items. All ten findings are CONFIRMED by probes; the follow-on cropping fault under F1 is PLAUSIBLE only.

Probe scripts and logs are in `reviews/691bed7/`; the PNGs the probes wrote are not committed.
