## Findings

### 1. The render-failure message still names the current backend, not the one that drew the window. Low, CONFIRMED.
- **Where:** `_render_window`, `src/AgentAPI.jl:364–365`:
  ```julia
  screen = Makie.getscreen(fig.scene)
  shown_by = isnothing(screen) ? _backend_name() : Symbol(nameof(parentmodule(typeof(screen))))
  ```
- **What:**
  - `Makie.getscreen(scene, backend = current_backend())` only returns a screen of the *current* backend (`Makie/src/display.jl:411`). So `shown_by` is always the current backend, which is the reported F5 again.
  - The GLMakie branch is wrapped now, and the advice (`reset_plotter!()`, choose the backend, relaunch) is better.
- **Evidence:**
  - GLMakie window, then `studio_headless!()`: "CairoMakie could not render the studio, which **CairoMakie** has drawn" (`g04.log`, `g01_gl.log`).
  - GLMakie window, then `WGLMakie.activate!()`: "which **WGLMakie** has drawn" (`g01_gl_then_wgl.log`).
  - WGLMakie figure, then `GLMakie.activate!()`: "which **GLMakie** has drawn" (`g01_wgl_then_gl.log`).
- **Fix:** Take the name from `fig.scene.current_screens`, preferring a screen whose backend differs from the renderer. Keep `getscreen(fig.scene, GLMakie)` only for the `px_per_unit` restore.
- **Test:** In plots-2, with the GLMakie window shown: `studio_headless!()`, then a heatmap_surface snapshot. The error message should contain "GLMakie has drawn". Then reactivate GLMakie.

### 2. Some paths still overwrite a drawing failure; one of them is new in this commit. Low, CONFIRMED.
- **Where:**
  - `studio_press!` → `_release_stale_view!` → `studio_reset_view!` (`AgentAPI.jl:855`, new in d84f756);
  - `studio_reset_view!` itself (`AgentAPI.jl:292`, unconditional `_status!(…, :info)`);
  - `_preset_row_action!` (`UILogic.jl:1406–1409`, the Files tab);
  - also the dead `:apply` branch of `_editor_row_action!`.
- **What:** None of these compare `manager.render_failures`.
  - A press that applies a pending change and releases the view reports "View reset: the plots follow the data." although the redraw failed: the counter went from 1 to 2 (`a02.log` A).
  - `studio_reset_view!()` with an option that fails to draw returns limits that are *not* the automatic view, (0.238, 0.362) × (0.369, 0.631), because the data step failed. It still says "View reset: the plots follow the data." (counter 5 → 6, `a02.log` D). `studio_reset_view!()` is the last step of the documented agent loop.
  - Applying a look preset whose `tick_format` can't be drawn reports "Applied look preset 'bad'." `:ok` (counter 1 → 2, `a04.log` A).
  - `studio_set!` (apply and release), the toggle, the tab reset and the mode switch keep the failure (`a02` B/E/F, `a04` B).
- **Fix:** In `studio_press!`, take the counter before `_press!` and restore the failure status after the release, as `studio_set!` does. In `studio_reset_view!` and `_preset_row_action!`, don't overwrite when the counter changed.
- **Test:** Zoom, set a broken `tick_format`, `studio_set!(:x_axis => :t; apply = false)`, then `studio_press!(:update_plot)`: expect `:error`. Then `studio_reset_view!()` with the broken option: expect `:error`.

### 3. A camera call between a pending change and its press keeps a stale view. Low, CONFIRMED.
- **Where:** `_view_context()` (`AgentAPI.jl:91`) reads the menu selections, not what is drawn. `_lock_view!` records it.
- **What:**
  - `studio_set!(:x_axis => :t; apply = false)`, then `studio_zoom!(4; center = (0.3, 0.5))`, then `studio_press!(:update_plot)`. The view is still locked, and the old limits (0.18–0.42 × 0.24–0.76) now apply to the t axis.
  - The same happens with `:plot_style => :heatmap_flat, :y_axis => :t` (pending) followed by Apply Layout. The heatmap shows only t ∈ [0.24, 0.76], which are solution values reused as times (`a06_C.png`). This is the symptom of the old F1, reached by a different order of calls.
  - The context recorded at the zoom already equals the pending one, so the press sees no change.
- **Fix:** Record the applied state in `_view_context`: `manager.active_plot_type`, and the axes and compare state of the last Update Plot / Apply Layout. Alternatively, store the pending flags (`manager.flags[:Plot|:Layout|:Simulation][]`) in `view_context` at lock time and release when a press clears them.
- **Test:** The `a06` sequence: expect `!camera_locked` and `ylims[2] >= 0.99` after the press.

### 4. A colour tuple for `colors` is still drawn as two colours (F7 not fixed in effect). Low, CONFIRMED.
- **Where:**
  - `studio_option!` now keeps the tuple, but the renderer does `colors[mod1(m_idx, length(colors))]` (`PlottingLogic.jl` around line 462).
  - `_option_type_reason` skips `:colors` entirely, because it is in `_COLOR_UI_KEYS`.
- **What:**
  - `studio_option!(:plot_style, :colors, (:red, 0.5))` stores `(:red, 0.5)`, but the methods are drawn alternately red and teal (the `0.5`). `h08_colors_tuple.png` is unchanged from the previous review. The UI tab does the same.
  - `colors = :red` is accepted, then the status shows "Drawing the look failed: MethodError: no method matching length(::Symbol)" (`a02.log` I).
  - The new test uses `[(:red, 0.5), :blue]`, which is already a vector and passes on 691bed7 and 47b4c6e too (`o02_*.log`).
- **Fix:** For `:colors`, wrap a single colour (`_valid_color(v) && !(v isa AbstractVector)`) into `[v]`, in both the API and the tab. Or reject non-vectors with "list of colours".
- **Test:** `studio_option!(:plot_style, :colors, (:red, 0.5))`, then all line primitives have the colour RGBA(1, 0, 0, 0.5); or the stored value is `[(:red, 0.5)]`.

## Minor issues

- **`screen.config.px_per_unit` is not restored** (`g04`/`g05` `cfgppu`).
  - Effects: `Makie.px_per_unit(screen)` (the PNG dpi metadata in `backend_show`) and GLMakie's scale-factor follow (`GLMakie/src/screen.jl:1010`). The latter only runs while `config.px_per_unit === nothing`, so after the first snapshot a window moved to a HiDPI monitor no longer rescales.
  - The framebuffer also stays at the snapshot size until the next frame is drawn (`g05`: 2518×1856 after 1.5 s idle).
  - Fix: restore the screen config as well.
- **The "Choose the backend before opening the studio…" advice is unconditional.** It is also given for a render failure without any backend switch (`shown_by == renderer`).
- **Stale `view_context`:** `reset_plotter!` and a CSV load without a camera leave it set (`a01` 3/8). This is inert today: every path that locks again resets it, and `_api_view_locked` needs `camera_locked`. Clearing it there would remove the trap.
- **Release before redraw:** Update Plot with only a pending *layout* change releases the view before anything is redrawn (`a01` 7). Harmless.
- **`studio_zoom!` with a broken tick format** throws the raw "Unmatched { in format expression" `ErrorException` out of the API (`a02` Z). Pre-existing.
- **Option gaps (parity issues, pre-existing):**
  - `hud.line_style = (:dash, :dense)` is rejected by the API, but the tab accepts and draws it (`a03_hud_tuple_style.png`).
  - A `LaTeXString` title is accepted, but the drawing fails (`set_axis_styles!` MethodError; reported).
  - Tuples are accepted for `color_range`/`lims`/`reference`/`points` but rejected for `markers`/`line_styles`. `_invalid_ui_reason` runs before the tuple conversion, despite the comment "a list option takes a tuple as its list".
- **Docs:**
  - `docs/src/agents.md` (line 107) and the `studio_view!` docstring still say only `studio_set!` releases the view. Neither mentions the release by `studio_press!` (also missing from its docstring), or that a Lock Camera press or a loaded camera makes the view the user's.
  - The CHANGELOG change itself is accurate.
- **Design note (unchanged):** pressing Lock Camera, then an API zoom, then a style change unlocks the camera entirely (`a01` 6). The API takes the user's lock over.
