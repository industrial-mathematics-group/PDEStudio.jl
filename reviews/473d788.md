## Findings

### 1. With the new Core, Run ignores a recorded copy's content, but the export and `load_config_file!` don't — medium — CONFIRMED (regression)

- **Where:**
  - `_include_sources` calls `_origin_of(src; unchanged = false)` (`src/ConfigIO.jl:344, 350`).
  - `save_params_to_csv` uses `_origin_of(src_path)`, which defaults to `unchanged = true`.
  - `manager.source_origins` is cleared only by `reset_manager!`: `load_config_file!` doesn't touch it, and an export that overwrites a bundle doesn't either.
- **What:** once a path is a recorded copy, Run treats it as its original for the rest of the session, whatever its content and however it was loaded. Three ways in:
  - **(a)** The user edits the copy, which the docs make the source. Run works (it runs as A), but the export of the same configuration records the copy itself as the origin. Reloading that export then runs it in the old bundle folder, and the unlisted helper is missing. So Run and export disagree, and the export doesn't reload.
  - **(b)** The user loads an edited copy with *Files → Load* (`load_config_file!`). The load runs it in B, with a helper the user put next to it (`uN() = 30`). Run runs it as A, with A's `u.jl` (`uN() = 20`). This is silent: the solver functions at Run differ from the load, and the results are cached under the same parameter hash.
  - **(c)** The bundle is overwritten by an export of another configuration, which is then loaded as `.jl`. Run runs that other configuration as A, with A's helper (20) instead of its own bundled one (50). This is exactly the case the test comment at `runtests.jl:530` says is protected ("the origin recorded for its old content doesn't apply to the new one"). It is protected only for the export.
  - With d302bc6, (b) and (c) ran consistently in B, and (a) failed at Run.
- **Evidence:** `probes/probe_origin_unchanged.local.out` cases 1–3. Against d302bc6 (`probe_origin_unchanged.oldsrc-local.out`), case 1 fails at Run and cases 2 and 3 give 30 and 50.
- **Fix:** one rule for Run and export. Invalidate entries when their meaning changes:
  - `load_config_file!(file)` deletes `manager.source_origins[abspath(file)]`, since it ran the file as itself.
  - `save_params_to_csv` deletes the entry of each `dst_path` it writes.
  - Then drop the digest, and the export records the origin for an edited recorded copy, which is what Run runs. Otherwise, keep the digest at Run as well and say in the status line why Run runs from the bundle.
- **Test:** the three cases of `probe_origin_unchanged.jl`:
  - Load, edit the copy, Run, export, reload: no failures.
  - `load_config_file!` of an edited copy, then Run: the helper next to the copy is the one defined.
  - The overwritten-bundle test extended with Run.

### 2. Skipping `:parameters`/`:curly` as a whole stops redirecting includes in keyword values — low — CONFIRMED (regression)

- **Where:** `_NO_VALUE_HEADS` now contains `:parameters, :curly, :braces` (`src/ConfigIO.jl:302-303`).
- **What:**
  - These forms ran the edited original at the export load and at Run (local Core), while the note said "the exported version ran":
    - `kwget(; v = include("h.jl"))`
    - `kwget2(1; v = include)`
    - `(; a = include("h.jl"))`
    - `Ref{typeof(include("h.jl"))}`
  - d302bc6 gave the copy for all four. Only the shorthand `(; include)` needed protecting.
- **Evidence:** `probes/probe_redirect_attack.{local,reg}.out`, first four rows: ORIGINAL. `probe_redirect_attack.oldsrc-local.out`: copy.
- **Fix:** don't skip `:parameters`. Keep its bare-`Symbol` arguments (the shorthand) and the name of each `:kw`, and redirect the values. `:curly` can stay skipped, or be handled the same way.
- **Test:** add `"kwget(; v) = v; kwget(; v = include(\"h.jl\"))"` to `forms` in "Bundled sources: include forms".

### 3. With the registered Core, an absolute include or a missing copy still runs the edited original at Run — low — CONFIRMED (residual of d302bc6 finding 1)

- **Where:** `_run_bundled_sources`, the `any_changed` rule. `_run_simulations` falls back to plain `run_all_simulations`.
- **What:**
  - The relative-include case is fixed: all copies run from B, so `include("h.jl")` finds the copy.
  - Two cases still run the edited original last, under the note "h.jl changed since the export: the exported version ran":
    - `cfg.jl` includes a listed helper by **absolute path**. Old probe K: "Running failed: edited original ran".
    - The **copy of `cfg.jl` is missing** and a listed helper was edited. The original `cfg.jl` is a source and includes the edited `h.jl` last (`hval() = 2`).
  - Side effect of the new rule, documented ("only bundled files are found"): with the registered Core, editing any listed helper now makes Run fail if `cfg.jl` uses an unlisted helper or a data file. In d302bc6 that Run worked, with the wrong helper.
- **Evidence:** `probes/old/probe_run_after_load.reg.out` K; `probes/probe_allcopies.reg.out` cases 2, 3 and 4.
- **Fix:** name both cases in the docs (absolute paths are already discouraged there). With the old Core, a cleaner route is to run `run_all_simulations` on a copy of the config with empty `sources` after `_include_sources`. But Core 0.4.3 then stores no source digests (`_source_metadata`), so that's the user's call. Releasing Core and requiring it removes the problem (a compat change).
- **Test:** `probe_allcopies.jl` case 4 under `!_CORE_SKIPS_SOURCES`, or a documented `@test_broken`.

### 4. More code that names `include` still breaks the export load, also with nothing edited — low — CONFIRMED (pre-existing, same in d302bc6)

- **Where:** `_redirect_includes`, which still replaces every `include` symbol in value position by a call.
- **What:**
  - These forms make the export load fail even with nothing edited:
    - `(include, b) = …` and `for (include, x) in …`: syntax error "Main is not a valid function argument name".
    - `@enum E include exclude` (in a module): "invalid argument for Enum".
    - `@isdefined(include)`: MethodError.
    - `f(::typeof(include))` dispatch, since the value is now a `_BundledInclude`.
  - Separately, `global g = include("h.jl")` and `local r = include("h.jl")` are not redirected: `:global` and `:local` are skipped whole, so they give ORIGINAL.
  - This round's fix covers keyword arguments, `let`, `for include in`, `(; include)` and `@NamedTuple`, as tested.
- **Evidence:** `probe_redirect_attack.*.out` rows "tuple destructuring", "for (include, x)", "@enum", "@isdefined", "typeof(include)", "global", "local". oldsrc gives identical results.
- **Fix:**
  - Keep the symbols of a tuple on the left of `=` (also in `for`).
  - Leave macro-call arguments that are bare `include` symbols alone.
  - For `:global`/`:local`, redirect only the right-hand sides.
  - Or document that a variable named `include` is unsupported in bundled code.
- **Test:** the nothing-edited rows of `probe_redirect_attack.jl` that fail.

### 5. The status line still says "define the solvers before running" after a failed source — low — CONFIRMED (d302bc6 finding 5 only partly fixed)

- **Where:** the `_status!` call at the end of `_run_bundled_sources` (and its docstring: "the solver functions must then be defined some other way").
- **What:** the docs now say that Run includes the sources again, and that the user should restore the file or remove it from the sources. The status line the user actually sees still gives the old advice, which can't work: Run includes the failing file again.
- **Evidence:** `probes/old/probe_staged.*.out` ("Source files of exp.csv failed; the parameters come from the CSV, define the solvers before running."); `old/probe_run_after_load.*.out` E.
- **Fix:** something like "…; restore the missing files and load again, or remove the file from the sources (*Advanced*)".
- **Test:** assert the text in the editors test that loads a failing source (`runtests.jl` ~1436).

  - Fix: varied padding (like `probe_digest.jl`), and assert `_content_digest` differs while `hash(read(copy))` doesn't.
- **Finding 4 has only a unit check** of `_origin_of(copy; unchanged = false)`. There is no end-to-end test of load → edit copy → Run, and none of the export after that (finding 1).

  - Absolute includes and a missing copy with the registered Core (finding 3).
  - The failure status text (finding 5).
- The test of code naming `include` checks only the nothing-edited export load, not Run with an edited helper.

## Minor issues

- A baremodule's own `include(p) = …` is bypassed whenever copies exist: "own include called: false" with h.jl edited. Same as d302bc6.
- `include` written inside a macro body, expanded later, isn't redirected (ORIGINAL). Same as d302bc6.
- CHANGELOG and docs say "once an original was edited"; the rule (`any_changed`) also applies when an original is gone.
- The docs don't say that an edited copy keeps running as its original at Run.
- Run after `reset_manager!` with the configuration kept still runs the copy in B and fails (`probe_run_semantics` case 7).

## Verdict

The commit fixes what d302bc6 was reviewed for:
- With the registered Core, relatively included edited helpers no longer run at Run.
- Variables, keywords and fields named `include` load.
- The digest covers whole files.
- An edited copy runs at Run.

Both suites are green, and the new tests fail on the old `src` for findings 1 and 2.

Two changes have side effects:
- `unchanged = false` at Run, without invalidating stale `source_origins`, makes Run disagree with the export and with `load_config_file!`. That includes a silent case where a different helper runs at Run than at the load, and the overwritten-bundle case the test claims to protect (finding 1).
- Skipping `:parameters` whole drops the redirection of keyword values (finding 2).

A few residual cases remain with the registered Core and in the status text.

Counts: 1 medium, 4 low (all CONFIRMED; findings 1 and 2 are regressions of this commit); 5 minor issues; 1 test-coverage gap (the digest test).
