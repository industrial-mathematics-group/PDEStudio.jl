## Findings

### 1. With the registered PDEStudioCore, Run includes edited originals of listed helpers, and their definitions win — medium — CONFIRMED

- **Where:** `_run_bundled_sources` (`src/ConfigIO.jl:439-447`): unchanged originals stay sources. `_run_simulations` falls back to plain `run_all_simulations` when `!_CORE_SKIPS_SOURCES`.
- **What:**
  - Take an export whose `cfg.jl` is unchanged but whose listed helper `h.jl` was edited. The sources become `[<bundle>/h.jl, A/cfg.jl]`.
  - The registered Core includes the copy, then `A/cfg.jl`. Its `include("h.jl")` (any form, and absolute paths too) loads the **edited original last**, so the solvers Run uses are the edited ones.
  - The status line meanwhile says "h.jl changed since the export: the exported version ran".
  - c8515ea gave the exported version here: every source was a copy, so the include found the bundled copy. This is a regression for the Core that CI and users have until the release, and it is the bug the CHANGELOG lists as fixed ("an edited helper included by relative path ran in place of its copy").
  - The CHANGELOG/docs limitation ("includes the copies of edited originals from the bundle folder") doesn't mention it.
  - The helpers test calls `_include_sources` directly (`runtests.jl:449-450`), and `abs_N` is checked only `if _CORE_SKIPS_SOURCES`, so the registered suite passes.
- **Evidence:**
  - `probe_run_semantics.reg.out` case 3: `Run 1: ["h v1 @B", "cfg v1 @A", "h v2 @A"]`, `hval() = 2`.
  - `probe_forms_run.reg.out`: every form gives `Run: ORIGINAL`.
  - `old_probe_run_after_load.reg.out` K: "Running failed: edited original ran".
- **Fix:** any of these:
  - Order the sources so that copies come after the originals. The last definitions are then the exported ones (an untested mitigation; include-time side effects still see the edited file).
  - With the old Core, keep c8515ea's "all copies" sources whenever one copy differs.
  - Release Core and require it (a compat change, the user's decision).
  - At least document the case exactly.
- **Test:** in the helpers testset, replace the direct `_include_sources` call with `_run_simulations(...)` and assert `helper_N() == 24` unconditionally.

### 2. `include` used as a variable, keyword or loop variable now breaks loading the export, even with nothing edited — low — CONFIRMED (regression)

- **Where:** `_redirect_includes`: `ex === :include && return …_BundledInclude…` replaces every bare `include` symbol in value position.
- **What:**
  - At the load, `copies` holds every bundled file that has an origin, so this applies to every export loaded with recorded origins, edited or not.
  - Code that worked as a `.jl` file and from c8515ea exports (which rewrote only `include(path)` calls) now fails to load:
    - `f(; include::Bool = true) = include ? …`
    - `let include = …`
    - `for include in files`
    - `(; include)`
    - `@NamedTuple{include::Bool}`
  - Its parameters then come from the CSV, with the "define the solvers" warning.
  - With the new Core the same happens at Run whenever a copy is a source.
- **Evidence:**
  - `probe_include_var.{local,reg}.out`: `failures = ["cfg.jl: TypeError: non-boolean (PDEStudio._BundledInclude) used in boolean co…"]`, `note = ""`.
  - `probe_forms_run.*.out`: the kwarg, `let`, `for`, named-tuple and `@NamedTuple` rows fail.
- **Fix:** don't substitute the symbol. Wrap value-position `include` as `_redirected(include, @__MODULE__, dir, copies)`. That function returns the bundled include only when the value `===` the module's global `include` (or `Base.include`/`Base.MainInclude.include`), and the value itself otherwise. Leave `:parameters` and `:curly`/`:braces` alone.
- **Test:** the `probe_include_var.jl` config in the include-forms testset, with unchanged originals.

### 3. The content digest misses edits of large files (finding 4 of c8515ea is still open for them) — low — CONFIRMED

- **Where:** `_origin_of` and `_run_bundled_sources:444`: `digest = hash(read(copy))`.
- **What:** `Base.hash(::Vector{UInt8})` hashes only about log(N) elements for arrays of 32768 elements or more (`_hash_fib`). For a source file of 32 KB or more, a same-length edit (a changed digit, the typical config edit) keeps the "digest", so a stale origin still applies:
  - the export records the old original for the edited content;
  - Run runs the edited copy as the original.
- **Evidence:** `probe_digest.*.out`: 156 B → 0/10 kept; 40 KB → 10/10 kept, and the export records `…/cfg.jl` (the original) instead of the copy.
- **Fix:** `hash(read(copy, String))`. String hashing covers all bytes (checked), and no new dependency is needed.
- **Test:** a file of more than 32 KB in the "bundle overwritten" testset.

### 4. A copy that stops matching its digest runs from the bundle folder at Run — low — CONFIRMED

- **Where:** `_include_sources`: `_origin_of` decides whether a copy runs as its original.
- **What:** two ways in:
  - The docs make the copies of edited originals the configuration's sources, so editing such a copy is a natural way to change the loaded configuration. After that edit the copy loses its origin. The next Run includes it plainly from `<name>_sources/`: unlisted helpers and data files are missing, and the copy no longer redirects other includes.
  - Same after `reset_manager!` when the config object is kept (`set_sim_config!(c)`).
  - Both now fail with a clear "Running failed" status, not silently.
- **Evidence:** `probe_run_semantics.local.out`, case 4 (`Run 2: FAILS: … exp_sources/u.jl`, `["cfg v3 @B"]`) and case 7.
- **Fix:** use the digest only for the origin an export records; at Run, keep running a recorded copy as its original. Or name the reason in the status line. Document it either way.
- **Test:** load, Run, edit the bundled `cfg.jl`, Run; assert "Simulation finished".

### 5. After a failed bundled source, Run can never succeed, but the docs say to define the solvers first — low — CONFIRMED (pre-existing, now visible)

- **Where:** `ran` keeps the failing file as a source; `docs/src/file_ops.md`, last bullet.
- **What:** Run includes the failing source again and fails ("Running failed: …"), whatever the user defines. The editors test even asserts this (`runtests.jl:1436`), while the docs promise that "the solver functions have to be defined before Run Simulation (e.g. by loading their package)".
- **Evidence:** `old_probe_run_after_load.*.out`, case E.
- **Fix:** either drop failed files from the sources used for Run (keep them for the export), or change the docs to "restore the missing file; Run includes the sources again".
- **Test:** a failed load, then define the solver, then Run → finished (or assert the documented message).

## Verdict

The commit fixes the main problem of c8515ea:
- With the new Core, a loaded export runs at Run exactly as it loaded, including unlisted helpers, data files, subfolders, absolute paths and deleted originals.
- Unchanged exports run with either Core.
- The include redirection now covers the common forms, keeps definitions and module names, and is tested.
- Run errors are visible, and the structural status line is fixed.
- All three suites are green, and the new tests fail on the old `src/`.

Open problems:
- Until Core is released, Run runs edited originals of listed helpers under a note that says otherwise (finding 1).
- The symbol-wide `include` replacement breaks loading of configs that name a variable `include` (finding 2).
- The digest uses a sampling hash (finding 3).
- Plus two smaller Run-semantics issues (findings 4 and 5).

Counts: 1 medium, 4 low (all CONFIRMED); 4 minor issues.
