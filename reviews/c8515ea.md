Reviewer: Claude Opus 5.5 (Anthropic), new session without the generating conversation

The main problem: **an export that loads now fails on *Run Simulation*.** PDEStudioCore re-includes the configuration's sources before every run. Configurations whose helpers aren't listed in `sources` (the default) or that read data files load correctly but can no longer run, even when nothing was edited. On f3ed3a2 they ran. ## Findings

### 1. A loaded export can't be run when it needs files that aren't bundled (unlisted helpers, data files, subfolders), even when nothing was edited — high — CONFIRMED

- **Where:**
  - `src/ConfigIO.jl:485` and `_relocate_sources` (`:391-404`): the sources are always the bundled copies.
  - `src/PDEStudio.jl:381`: `simulation_trigger` calls PDEStudioCore's `run_all_simulations`, which starts with `_load_sources(config.sources)`, a plain `Base.include(mod, abspath(file))` of every source (`PDEStudioCore/src/Simulations.jl:220-226, 306`).
- **What:**
  - c8515ea runs the copies "as the originals" with `include` redirection **only at load time**. *Run Simulation* includes every source again. The copies are now always the sources, so they run from `<name>_sources/` as themselves, without the as-original path and without `_redirect_includes`.
  - Anything that `@__DIR__` or a relative include reaches next to the original is missing there: unlisted helpers (the default, because `load_config_file!` lists only the file itself), data files (docs rule 4), and listed helpers in subfolders (the bundle is flat). The Run fails, also when the originals are unchanged.
  - On f3ed3a2 (and a515df4) unchanged originals stayed the sources, so Run worked. So finding 1 of f3ed3a2 is fixed only for the load: the user gets "Loaded exp.csv. Run Simulation to apply it." and Run throws.
  - The click handler throws out of `simulation_trigger`, which has no `try`. The status line keeps "Loaded exp.csv…", so nothing tells the user what happened.
  - For a listed helper included by absolute path, Run re-includes the *edited original* over the exported definitions, so the run doesn't use the exported code, against the rule.
  - Pre-existing, same mechanism: after a failed source ("define the solvers before running", `docs/src/file_ops.md`), the failing copy is a source, so Run always throws, whatever the user defines.
- **Evidence:**
  - `probe_run_after_load.out`:
    - C: `Run: THROWS SystemError: opening file "…/exp_sources/u.jl"`
    - D: `… "…/exp_sources/n.txt"`
    - K: `THROWS edited original ran`
    - E: failed source, always throws
  - `probe_run_after_load_oldsrc.out` (f3ed3a2): C and D run, "Simulation finished".
  - `probe_run_subfolder.out`: `Run: THROWS … exp_sources/lib/h.jl`.
- **Fix:** Run has to execute the sources the way the load did. Options:
  - **(a) Preferred.** Record per source how it ran (`runs_as`, `copies`) and re-run it with `_include_as` before calling Core. Pair this with a PDEStudioCore option that skips or replaces `_load_sources`, e.g. `run_all_simulations(config; load_sources = false)` or an include hook. Core lands first, as the project rules require; the source digests in the metadata stay unchanged.
  - **(b) Interim.** Keep the originals as the sources while they are unchanged (the f3ed3a2 behaviour), and use the copies only for edited or missing originals. Document that in that case Run only finds bundled files.
  - Either way, catch errors from `run_all_simulations` in `simulation_trigger` and show them in the status line.
- **Test:** in the editors group, load an export of (1) a config with an unlisted helper, (2) a config reading `n.txt` via `@__DIR__`, (3) a config with a listed `lib/h.jl`, all with unchanged originals, then click *Run Simulation*. Assert "Simulation finished" and the plotted N. Add (1) and (2) again with an edited config.

### 2. Some include forms bypass the redirection: the edited original runs while the note says the exported version ran — medium — CONFIRMED

- **Where:** `_redirect_includes` (`src/ConfigIO.jl:274-283`). It rewrites only calls of exactly the form `include(path)`, with the symbol `:include` and one argument.
- **What:** `include(mapexpr, path)`, `Base.include(@__MODULE__, path)`, `foreach(include, files)` and `include.(files)` aren't rewritten. Running as the original, they include the edited original files. The status line still says "h.jl changed since the export: the exported version ran", which is false. On f3ed3a2 all four ran the copy (from the bundle folder). `foreach(include, …)` is a common idiom for helper lists.
- **Evidence:** `probe_include_forms.out` gives `ORIGINAL N0 = 1, N = 2, note = "h.jl changed since the export: the exported version ran"` for the four forms. `probe_include_forms_oldsrc.out` gives `copy` for all four.
- **Fix:**
  - Also rewrite `include(f, p)` (3 arguments), `Base.include(m, p)` and `Base.include(f, m, p)`, and replace a bare `include` used as a value (not a definition) with a closure over `_bundled_include`.
  - Or, more robust, detect the include of a listed original at run time and correct the note: `Base.include_callbacks` sees every include, whatever its form.
- **Test:** the four forms in the bundled-sources helpers testset, each with an edited listed helper; assert the copy's value.

### 3. The rewrite breaks code that defines its own `include` (the baremodule pattern): the export fails to load — low — CONFIRMED

- **Where:** `_redirect_includes` also rewrites call signatures on the left of `=` or `function`.
- **What:** `baremodule BO; using Base; include(p) = Base.include(BO, p); include("h.jl"); end` loads as a `.jl` file. Its export fails once any copy differs from its original, or as soon as `copies` is non-empty, i.e. always for exports with recorded origins. The error is `syntax: "BO" is not a valid function argument name`. It loaded on f3ed3a2.
- **Evidence:** `probe_include_forms.out`, "baremodule …": `FAIL`. Old src: `copy`.
- **Fix:** don't descend into the signature of a definition: the first argument of `:function`, or of `:(=)` when it is a `:call`, `:where` or `:(::)`.
- **Test:** this baremodule config in the bundled-sources testset.

### 4. `manager.source_origins` can record the wrong project's paths — low — CONFIRMED

- **Where:** `src/ConfigIO.jl:332-334` (entries are only added), `:864` (the lookup at export), `reset_manager!` (the only place that clears the map).
- **What:**
  1. Load an export `D/exp.csv` of project A. The map now holds `D/exp_sources/cfg.jl → A/cfg.jl`.
  2. In the same session, export project B (same file names) to `D/exp`, overwriting the bundle.
  3. Load `D/exp_sources/cfg.jl` as a `.jl` file and export again. The new export records `A/…` as the origins of B's content.

  Reloading it runs B's code *as `A/cfg.jl`*: unlisted files and data come from A's folder, and the note says that both files changed. The same happens when a user edits a bundled copy and loads it as `.jl`. The other sequences checked (chains, re-exporting over the loaded export, staged rebuild) are correct.
- **Evidence:** `probe_chain.out`, "stale entry": `E/exp2 origins: [A/h.jl, A/cfg.jl] (content is B's)`, and the reload note "h.jl changed …; cfg.jl changed …".
- **Fix:** store the content hash with the origin, e.g. `copy => (origin, hash)`, and use the entry only while the copy still has that content. Or drop entries for files that `save_params_to_csv` overwrites, and for a file loaded by `load_config_file!`.
- **Test:** the sequence above; assert that the origins are B's paths or the copy paths.

### 5. Structural loads: the note is cut off, and failures of bundled sources aren't shown — low — CONFIRMED

- **Where:** `_handle_load` (`src/UILogic.jl:403-408`); `_wrap_status` (2 × 76 characters).
- **What:**
  - The structural message alone is about 140 characters, so the appended note is always cut: "(h.jl changed si…".
  - The branch also calls `_status!` unconditionally, which replaces the "Source files of exp.csv failed; … define the solvers" warning that `_run_bundled_sources` set. The failure is invisible until Run.
  - The second part is pre-existing, but this commit edited exactly this branch for finding 2 of f3ed3a2.
  - In the non-structural branch, notes for two or more files also cut off "Run Simulation to apply it." The notes are now also logged with `@warn`, which helps.
- **Evidence:** `probe_staged.out`:
  - `structural status: … (save a preset first to keep the current settings). (h.jl changed si…`
  - with failures `["h.jl: missing", "cfg.jl: …"]` the status is only the structural text.
- **Fix:** put the note (or the failure) first and shorten the structural text, e.g. "h.jl changed since the export (exported version ran). Run Simulation rebuilds the window." Keep the failure warning when `source_failures` isn't empty.
- **Test:** in the editors group, a structural `_handle_load` of an export with an edited helper and one with a failing source; assert the file name and "failed" in `status()`.

### 6. Docs and CHANGELOG promise more than the implementation does — low — CONFIRMED (follows from 1–3)

- **Where:** `CHANGELOG.md:26-31`, `docs/src/file_ops.md:42-50`, `docs/src/index.md:160`.
- **What:**
  - "files that aren't bundled … are found there" holds only for the load, not for Run (finding 1).
  - "an `include` of a bundled file runs its copy" holds only for `include(path)` (finding 2).
  - "if an original's folder is gone, its copy runs from `<name>_sources/`, where it finds the other bundled files" isn't true for subfolders: `include("lib/h.jl")` fails (`probe_include_forms.out`, sub-gone). This also failed on f3ed3a2. The new redirection could fix it by running as the original even when its folder is gone, because includes of listed files are mapped to their copies.
- **Fix:** fix 1 and 2, or document the limits. Consider always running as the original, with the bundle folder as a fallback only for exports without recorded origins.
- **Test:** the sub-gone case of `probe_include_forms.jl`.

## Minor issues

- `_relocate_sources` and the export resolve relative `sources` entries against the working directory. An unrelated `h.jl` in the working directory becomes a source, gets bundled and is re-included at Run (`probe_chain.out`, last case). Pre-existing.
- A function body that calls `include` later stays redirected to the copies of that export for the rest of the session (`loadD()` → 1). Probably intended, but undocumented.
- `_char_literal_start` treats the field access `x.in'` as a Char start. Contrived; `_raw_text` never produces it.
- `read(origin(i))` reads whatever path a CSV names, in full. This happens only after the run-code confirmation, so it is negligible.

## Verdict

Most of the commit is good:
- **The load path is redesigned well:** with redirected includes, copies running as their originals give a correct load in nearly every case tried. That covers unlisted helpers, data files, old-format exports, absolute paths, missing copies, symlinks, module blocks, nested and function-body includes, `@__FILE__`, and chains of 4 generations with moved, deleted and recreated originals.
- **Findings 2–7 of f3ed3a2 are fixed** and have tests, and the suite is green.

Four things are still wrong:
- **The load and Run behave differently (high).** PDEStudioCore re-includes the sources at *Run Simulation*. Since the copies are always the sources now, every export that needs an unbundled file or a subfolder can't be run, even when nothing changed. That is a regression from f3ed3a2, which the tests miss because none of them runs a loaded export.
- **Some include forms run the edited originals** under a status line that says otherwise (medium).
- **Code that defines its own `include` no longer loads from its export** (low).
- **Smaller issues (low):** a stale origin after a bundle is overwritten, the cut-off structural note, and docs and CHANGELOG wording that follows from the above.

Counts: 1 high, 1 medium, 4 low (all CONFIRMED); 4 minor issues.
