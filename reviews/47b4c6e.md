## Findings

### 1. The view release misses style, compare and layout changes. Medium, CONFIRMED.
- **Where:** `_api_view_locked` (`src/AgentAPI.jl:105–107`) tells an API lock from a user lock by `manager.view_context.cache === manager.camera_cache`. `rebuild_plot_layout!` (`src/MakiePlotting.jl:414–419`) calls `extract_and_store_camera_state!` whenever the camera is locked, and that call assigns a **new** Dict to `manager.camera_cache`.
- **What:**
  - Every *Apply Layout* change (style, compare target/columns/link, plot size, legend) rebuilds the layout. That replaces the cache, so the API lock then looks like a user lock and `_release_stale_view!` never fires.
  - The commit message, the `studio_view!` docstring and `docs/src/agents.md` all promise a release when "the plot style or the comparison" change. Only the menus that apply with *Update Plot* (x/y/z/u) actually release.
  - Example: `studio_zoom!(4; center = (0.3, 0.5))`, then `studio_set!(:plot_style => :heatmap_flat, :y_axis => :t)`. The result is `camera_locked = true`, and the y limits are (0.24, 0.76) from the solution values, now applied to the *time* axis.
  - The same happens with `compare_target => :methods` (4 subplots locked to the old limits) and with switching to a particle (Lagrangian) style, since that is also a style change.
  - After any layout change, a later x-axis change no longer releases the view either.
  - Separately, `studio_set!(:x_axis => :t; apply = false)` followed by `studio_press!(:update_plot)` keeps the stale view, because the release only runs inside `studio_set!` with `apply = true`.
- **Evidence:** `h01.log` sections B and F; `h02.log` A; `h02_A_heatmap_after_zoom.png` (window 0.18–0.42 × 0.24–0.76 of x × t) vs `h02_A_heatmap_reset.png`.
- **Fix:** Don't use the identity of the cache as the marker. Record who owns the lock, e.g. `manager.view_owner = :api` set in `_lock_view!` and set to `:user` in the Lock Camera handler and the CSV/preset camera load. Alternatively, have `extract_and_store_camera_state!` update the existing Dict in place. Also call `_release_stale_view!` from `studio_press!(:update_plot / :apply_layout)`.
- **Test:** Zoom, then `studio_set!(:plot_style => :heatmap_flat, :y_axis => :t)`: expect `!camera_locked` and ylims covering [0, 2]. The same for `compare_target => :methods`, and for zoom, then `plot_width` change, then x-axis change.

### 2. `_option_type_reason` checks against the current value, so the API locks itself out of valid values. Medium, CONFIRMED.
- **Where:** `_option_type_reason` (`src/AgentAPI.jl`, end of the file), which uses `target[key]` (the current value) as the type reference.
- **What:**
  - **Int/Float lock-in:** `studio_option!(:plot_style, :line_width, 2)` is accepted (old value is Real). After that, 2.5 and even the default 3.0 are rejected as "not a valid whole number". The same happens for `:padding` 0, then 0.05. The UI tab accepts 2.5 in that state (`h03.log`), and a value typed into the tab or loaded from CSV causes the same lock-in for the API.
  - **Floats rejected:** Int-default options reject floats that the tab and Makie take, e.g. `axis_general.font_size = 20.5`.
  - **Strings in Symbol options:** these options accept a String, which the tab rejects ("not a valid value"). `studio_option!(:plot_style, :line_direction, "horizontal")` stores a String. On lines_2d the redraw then fails (`MethodError: build_2d_lines_grid(…, ::String)`, because `dir::Symbol`). After that, the repair `studio_option!(…, :line_direction, :horizontal)` is rejected as "not a valid text (a String)". The API can't recover until a reset. `hud.line_style` behaves the same way.
- **Evidence:** `h02.log` B; `h06.log`.
- **Fix:**
  - Take the type from the built-in default (`MASTER_UI_DICT` via `_ui_default`), not from the current value.
  - Accept any finite Real for Real defaults, and require Integer only where it matters (`levels`, `tick_count`, `method_index`, …).
  - For Symbol options, accept only Symbols, or convert a String to a Symbol.
- **Test:** `line_width` 2, then 2.5, then 3.0 all succeed. `line_direction = "vertical"` is either rejected or stored as `:vertical`.

### 3. The failed-redraw status is lost in common paths; the CHANGELOG entry overclaims. Medium, CONFIRMED.
- **Where:**
  - The status-text comparisons in `studio_option!` (`_status_text() == before`) and `studio_set!` (`_status_text() != before`).
  - `_apply_editor_input!` (`src/UILogic.jl`, around line 2023), which always calls `_status!(_change_message(…), :ok)` after `_after_editor_change!`. The toggle path in `_editor_row_action!` does the same.
- **What:**
  - **UI tab:** typing `"{:nope"` as `tick_format` on the tab fails the redraw. The new error status is immediately replaced by "X Axis (1D) → tick_format = {:nope" `:ok`. The tab is the GUI's main way to set options, so the CHANGELOG line "A plot that can't be drawn … says so in the status line" doesn't hold for it. It does hold for Update Plot, slider moves and the API.
  - **Repeated identical failures:** if the status already shows the same error text, a second failing call isn't detected. For example, with `tick_format` still broken, `studio_option!(:x_axis_1d, :grid_visibility, false)` returns "… grid_visibility = false" `:ok`, and `studio_set!(:plot_style => :scatter_1d)` returns `:ok`, although both redraws fail again (the log shows the `@error` each time).
  - **Normal use:** no misfires. The single-process suite produces no render errors.
- **Evidence:** `h03.log`, `h04.log`.
- **Fix:** Add a counter (`manager.render_failures`) that both catch blocks increment. Compare it before and after in `studio_option!`, `studio_set!`, `_apply_editor_input!` and `_editor_row_action!`, and don't overwrite the status when it changed.
- **Test:** Through `_apply_editor_input!`, a failing `tick_format` leaves `status.level === :error`. Two consecutive failing `studio_option!` calls both report `:error`.

### 4. `px_per_unit` changes the GLMakie window's resolution. Low, CONFIRMED.
- **Where:** `_render_window`: `Makie.colorbuffer(fig; px_per_unit = ppu)` reuses the displayed screen and applies the new config to it.
- **What:**
  - After `studio_snapshot(…; px_per_unit = 2)`, the live window's screen has `px_per_unit = 2` (render buffer 2518×1856 for a 1259×928 window). It stays that way until the next snapshot.
  - A window opened with `GLMakie.activate!(px_per_unit = 2)` (a HiDPI setup) is reset to 1 by a default snapshot.
  - The window size and limits stay the same, but the docstring promises "without changing the window".
- **Evidence:** `g03.log`, `g01_gl.log` (`scrinfo`).
- **Fix:** Save `screen.px_per_unit[]` (or the screen config) before rendering and restore it afterwards. Alternatively, render other resolutions in a separate invisible GLMakie screen.
- **Test:** In plots-2, the screen's `px_per_unit` is the same before and after `studio_snapshot(…; px_per_unit = 2)`.

### 5. After a backend switch, snapshots fail with misleading messages. Low, CONFIRMED (corner case).
- **What:**
  - A GLMakie window, then `studio_headless!()` (or `WGLMakie.activate!()`), then a heatmap_surface snapshot gives "CairoMakie could not render the studio **while CairoMakie shows it** … work without a display (studio_headless!())". The named backend is wrong (it is `current_backend`, not the one showing the figure), and the advice doesn't help: the probe called `studio_headless!()` and still failed.
  - The other way round (a figure already rendered by CairoMakie, then `GLMakie.activate!()`), the raw "Cannot register computation …" escapes unwrapped.
  - WGLMakie serialisation doesn't conflict (`g02`), so the browser case is fine as far as I could simulate it.
- **Evidence:** `g01_gl.log` (end), `g01_wgl_then_gl.log`, `g01_gl_then_wgl.log`.
- **Fix:** Name the backend from `Makie.getscreen(fig.scene)`. Advise relaunching the studio (`reset_plotter!()`, then `launch_plotter` after choosing the backend). Wrap the GLMakie branch too.

### 6. The new tests don't pin the F6 and F2 fixes. Low, CONFIRMED.
- **What:**
  - **Colorbar test:** `cmap > 200` counts saturated pixels in the rightmost 120 columns, and the heatmap itself is colourful. Replayed with 691bed7's `src/` (crop without colorbar), cmap = 43600, so the test passes. With the new `src/` it is 10758.
  - **GLMakie volume test:** `length(unique(img)) > 50` is also true for empty axes: an empty CairoMakie 3D snapshot has 817 unique colours. Old `src/` never sets `:warn`, so only the heatmap_surface iteration catches the old code.
- **Evidence:** `o01_old.log` / `o01_new.log`, `o01_decoupled1_old.png` (no colorbar) vs `_new.png`; `h05_volume.png`.
- **Fix:** Require the snapshot width to be at least the axis box width plus the colorbar width, or look for a vertical gradient column at the right. For the volume, compare the pixel variance inside the axis box against a CairoMakie render of the same figure.

### 7. `studio_option!` turns a colour tuple into a list of colours. Low, CONFIRMED.
- **Where:** `target[key] = value isa Tuple && target[key] isa AbstractVector ? collect(Any, value) : value`. This runs after `_invalid_ui_reason` has accepted the tuple as a single colour.
- **What:** `studio_option!(:plot_style, :colors, (:red, 0.5))` (semi-transparent red, the form the validation message itself suggests) is stored as `Any[:red, 0.5]`. The methods are then drawn alternately red and teal (`h08_colors_tuple.png`). The UI tab stores the tuple.
- **Fix:** Don't convert for the colour keys, or validate the converted value.

### 8. The method hint in `describe_studio` lists the methods in the wrong order. Low, CONFIRMED.
- **What:** For heat_2d it prints "shows the i-th of exact, explicit, adi", but `method_index` 1 shows explicit, 2 shows adi and 3 shows exact. Out-of-range values (4) silently show exact.
- **Evidence:** `h09.log`.
- **Fix:** List the methods in the renderer's `method_index` order, e.g. "1 = explicit, 2 = adi, 3 = exact", and reject out-of-range indices.
