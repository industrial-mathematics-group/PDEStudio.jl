Deep Dive: File Operations & Execution

The Files tab (name / path and description boxes, loading, export, presets) and the execution buttons below the tabs handle serialization and execution. Because PDE simulations and 3D graphics can be computationally heavy, this region works with a lock system that keeps the UI responsive.

🚦 The Reactive State Machine (Triggers & Locks)

To keep the Makie rendering engine from stuttering while the backend computes, the studio uses hierarchical locks: Simulation → Layout → Plot.

The three execution buttons (Run Simulation, Apply Layout, Update Plot) are your traffic lights:

  • Green (Synced): The plot matches the backend data and your UI settings.
  • Yellow (Pending Action): You changed something, and the studio waits for you to confirm it with a click on the yellow button.
  • Coral / Red (Locked): A higher-priority action is required first. For example, after changing a physics parameter, Apply Layout and Update Plot stay locked until you click Run Simulation.

Simulations that already exist on disk (same parameters, same hash) are loaded instead of recomputed.

📂 Loading a Saved State

In the Files tab, choose the file with Browse… (the system's file dialog; in a browser, an upload), type its path into the Name / path box and click Load, or drop it anywhere onto the window; the status line reports the result. A bare file name is enough: the studio searches the working directory, the figures and animations folders of the figure path and of the save path, the preset folders and ./Experiments (each including one level of subfolders; a name without extension means a CSV). The same works from code: set_sim_config!("my_run.csv"), set_sim_config!("configs/euler2d.jl").

Two kinds of files can be loaded:

  • CSV files (exports and presets): values only, parsed safely. A CSV that names a blueprint (the code that builds its configuration, see below) runs that code when it loads; a CSV without one never runs code.
  • Julia files (.jl) whose last expression is the SimulationConfig, or a function without arguments (no positional, optional or keyword arguments) that returns it; anything else is an error. The file runs in the target module (set_target_module!) and becomes the last of the configuration's sources (moved there if the configuration lists it elsewhere): runs include it after the helper files, so it may use and override what they define, and exports copy it into their blueprint.

⚠️ Code execution: loading a Julia file, or a CSV that names a blueprint (see below), runs that code with your rights. Only load files you trust. In the studio, such a file needs a second click on Load: the first one only shows the warning in the status line. The second click confirms that file as it was at the first one: the file itself and, for a CSV, its blueprint (the digest of its files, which is all the code it runs, or its function); another file under the same name (a new upload) or a change in between asks again. A blueprint that ran in this session doesn't ask again: other CSV files with the same blueprint load with one click. For a Julia file, the files its code includes (include("helper.jl")) are not covered: a change of those between the two clicks runs without a new warning.

The load button turns green when the file was read; press Run Simulation to compute and show it.

File dialog: Browse… uses the tools the operating system brings: AppleScript on macOS, PowerShell on Windows, zenity or kdialog on Linux (GNOME, KDE and most desktops install one of them; otherwise install zenity, or type the path or drop the file). PDEStudio.FILE_DIALOG[] can be replaced by any function returning a path.

In a browser (WGLMakie): Browse… opens the browser's own file picker, and files can be dropped onto the studio; both upload the file to the computer running Julia, so a studio served from a remote compute node loads configurations from your own computer. The files are stored under <save path>/Uploads/<name>/ and loaded like the Load button (files that run code ask for the second click). Choose (or drop) the files that belong together at once: a CSV with the files of its blueprint folder (the source files and its blueprint.csv, which tells the studio where each file belongs), or a Julia file with the helpers it includes relative to @__DIR__; they are stored where the loader finds them. A browser's file picker and a drop take files of one folder: a blueprint whose files lie in subfolders (lib/solvers.jl) can't be chosen together with its CSV. Copy such an export (the CSV and its blueprint folder) to the computer running Julia and load it there. Uploads are limited to 20 MB per file. If the browser doesn't open the picker right away (it only does so shortly after a click), a small panel asks for one more click on Choose file….

If the file needs more parameter sliders or other physical dimensions than the open window has, the buttons turn orange: the configuration is staged, and the next click on Run Simulation rebuilds the whole window with the new limits, applies the file and runs it. (Save your current look as a preset first if you want to keep it.) Without an open window, the limits are applied directly.

🧩 Blueprints and Realizations

A configuration has two parts. Its blueprint is the code that builds it: the configuration file with the files it includes, or a function of a package. A CSV file is a realization of a blueprint: it holds the concrete values (resolution, parameters, the sweep, which methods are active) and names the blueprint. Several CSV files can name the same blueprint: one general configuration, and a file per resolution, method or figure.

An export writes both. Next to <name>.csv, the code is copied into a folder named after the configuration file and the content of the code, e.g. dmr-3fa9c2e1/:

  • the files of sources, and the files they include themselves (helpers such as include("lib/solvers.jl"), recorded when the configuration file is loaded and at every Run Simulation; no need to list them), each with its path relative to the folder they all lie in, so relative includes find the copies;
  • blueprint.csv, which says what the folder holds: the sources in their order, the other files, what builds the configuration (the last source, a function, or nothing) and the digest (SHA-256) of all of it: the files with their paths, and what builds the configuration. Changing any of it makes another blueprint.

The eight digits in the folder's name are the start of that digest. Exports with the same code share the folder, exports with other code get another one, and a folder that holds another blueprint is never overwritten (the export fails instead). Keep blueprint folders byte for byte, also in git (* -text in a .gitattributes): converted line endings are other files. The CSV names the folder (Metadata, General, blueprint) and pins the digest (blueprint_digest).

Loading a CSV that names a blueprint checks the folder (every file is there, and the files are the ones the digest was made of: a blueprint runs as it was exported, or not at all), runs it, and applies the CSV's rows to the configuration it builds:

  • the folder runs on its own: its sources are the copies, the originals are not looked at, and an include of any file the blueprint doesn't list (outside the folder, or added to it later) is refused before that file runs. The sources of a loaded export can't be changed (e.g. in the Advanced tab): load the .jl file for that. To change the code, load the configuration's .jl file instead: a CSV reproduces, a .jl file develops (and its next export gets a new folder);

  • an export (Metadata, General, mode, replace) is the whole realization: the shared parameters, the sweep, the active methods and their parameters are the file's. The blueprint's other methods stay available in the Methods tab: the CSV decides which methods are active, the blueprint offers the pool;

  • a file written by hand (no mode row) is a patch: only what it lists changes, everything else is the blueprint's. A whole realization can be as short as this:

    Category,Scope,Parameter,Value Metadata,General,blueprint,dmr-3fa9c2e1 Simulation,Shared,Grid_Ns,"(800, 200)" Simulation,Config,defaults,"[:mood_u2]"

  • the blueprint always runs when the file loads (it defines the solvers, the post-processor and the statistics the values need). In the window this asks once per blueprint and session: a second file with the same blueprint loads without another click;

  • Run Simulation checks the folder again: a file changed since the load stops the run.

A function as the blueprint. A configuration that a function of a package builds has no file. Bind the function itself, launch_plotter(test_advection_1d) or set_sim_config!(my_package_config) (HyperCloud's @plot name does): exports name it (Metadata, General, blueprint_function), and loading one calls it again. The function is found by its name in the target module (set_target_module!), like solvers. A configuration bound as a value (launch_plotter(test_advection_1d())) has no blueprint: its exports hold values only.

A CSV without a blueprint holds values for solvers of packages: it loads without running code, in a session that has the packages loaded. It can't hold objects.

Objects come from the blueprint. Values the CSV can only hold as text, objects such as a struct (a boundary condition), an enum or a container holding one, are written as Object rows with the scopes of the Simulation rows (Object, Shared, bc, Wall(id=1), Object, upwind, flux, …, Object, Sweep, ic, …). The loader takes each from the blueprint's configuration, at the same parameter (shared, the same method, or the sweep), and checks that it has the text the CSV holds. A value whose text is too large or deep for the CSV parser (more than 10⁶ elements, nesting deeper than 32) is an object, too. Objects are never changed in the studio (the editors refuse them), so change them in the configuration file and load that. Loading fails with an error naming the parameter if:

  • the blueprint's configuration has no such object there, or another one, or the file has no blueprint that builds a configuration;
  • a Simulation row sets a parameter whose key is an object anywhere in the blueprint's configuration (shared, a method or the sweep: a struct and its text have the same identity, so the text would silently replace the struct; the same holds for simulation presets and the bound configuration);
  • a parameter has both a Simulation and an Object row.

Functions are no parameters (PDEStudioCore can't tell runs apart by them; give them a name or a struct instead): an export of a configuration PDEStudioCore refuses warns that it can't run.

What a blueprint folder doesn't hold, and so can't use:

  • files included by an absolute path (the copy is in the folder, but the include still names the original: loading is refused). Include relative to the file: include("solvers.jl"), include(joinpath(@__DIR__, …));
  • data files the code reads (meshes, tables): they are not copied. Keep them in a package, or build the data in code;
  • code that is loaded in other ways than include (Base.include_string on a text that is read, an include in another task such as @async or Threads.@spawn): it is neither recorded nor checked;
  • files that are only included in some runs (isfile(p) && include(p)): only the files that were included when the configuration was loaded or run are copied, and a loaded blueprint runs exactly the files it lists.

A configuration that was bound as a value but lists source files (SimulationConfig(…; sources = ["solvers.jl"]) in a script) gets a blueprint of code only: the folder runs when the export loads, and the CSV is the whole configuration (without objects).

Configuration files that reload reliably, from the studio and from any blueprint folder:

  1. End with the configuration: the last expression is the SimulationConfig, or a function without arguments that returns it (() -> SimulationConfig(...), get_config() = SimulationConfig(...) followed by get_config; not get_config(N = 12): a function with arguments is refused); nothing interactive (no launch_plotter(), no display).
  2. Objects in the configuration file: structs and other objects among the parameters are created by the file that returns the configuration (or its helpers), never by the studio or the CSV.
  3. No absolute paths: include helper files relative to the file (include("solvers.jl") or include(joinpath(@__DIR__, "solvers.jl"))); they are copied into its blueprint. List a file in sources (sources = [joinpath(@__DIR__, "solvers.jl")]) if the configuration's file doesn't include it itself (code that was loaded before, e.g. by your startup script).
  4. Solvers in a package are the most robust: using MySolvers at the top, and the blueprint only holds the configuration. Packages must be installed in the environment that loads the file.
  5. Data files (meshes, initial conditions) are not copied: a loaded export doesn't find files that were read relative to @__DIR__. Keep them in a package (or generate them in code).
  6. Post-processor, reference and statistics too: an export records only their names, and the statistics are global (not part of the configuration). Define the post-processor, the reference, custom statistics (register_stat! + calc_stat) and the set_stat_preset! call in a file of sources, or in a package.

An export checks this: solvers, reference, post-processor and statistics defined neither in a file of the blueprint nor in a package (e.g. in the REPL, or in a script that isn't a source) are named in the status line and the log, and recorded in the CSV (Metadata, General, code_outside_sources): the export can't run them elsewhere. The CSV also lists the registered statistics (statistics); loading it warns about the ones the session doesn't register (after its blueprint ran). An export with objects that nothing builds again (a configuration bound as a value) warns that the CSV can't be loaded.

# configs/advection.jl
using PDEStudio
include("solvers.jl")                    # defines advection_1d (relative to this file)

SimulationConfig(create_param_dict(:N => 100, :cfl => 0.5, :sim_func_name => :advection_1d),
                 create_method_dict(:upwind => create_param_dict(:scheme => "upwind")), [:upwind];
                 varied = create_varied_dict(:cfl => [0.3, 0.5]),
                 sources = [joinpath(@__DIR__, "solvers.jl")])   # (optional: the file includes it itself)

💾 Exporting (Images & Animations)

The Name / path box is also the gateway for saving your work. Exports land in <figure path>/figures (static frames; with the export option create_savefolder, in a subfolder per name) and <figure path>/animations. A path in the name (study/run_1, or an absolute path) is honoured.

The figure path is the save path of the data unless set_figure_path! sets another folder. When the data lies on a remote machine, e.g. a server drive mounted locally and given to set_save_path!, this keeps figures, animations and snapshots on your own computer while the cached runs stay on the server:

set_save_path!("/mnt/cluster/results")   # the data
set_figure_path!("~/Pictures/study")     # figures, animations, snapshots
get_figure_path()                        # where exports go now
set_figure_path!()                       # back to the save path

The Direct Format Trick: By default, Export saves the figure in every format listed in the export setting save_formats (Files → Settings ›, usually png). Typing an extension into the filename bypasses that list:

  • Static formats (png, jpg, jpeg, pdf, svg, eps): my_figure.svg exports exactly that one file.
  • Animations (mp4, webm, mkv, gif): select a variable in the Anim Target dropdown (e.g. t), type my_video.mp4 and click Export. The studio locks the camera and records the target's whole slider range (duration and frame rate: animation_time and animation_FPS in Files → Settings ›).
  • Anything else is part of the name: run_dt0.5 exports run_dt0.5.png (and the other listed formats).

Note: All exports are pristine. The studio renders a fresh copy of the plot for the export, so UI artifacts (slider handles, unapplied states) never appear in your files.

🎨 Presets vs. Full Exports

ButtonSavesTypical use
ExportThe figure/animation and a CSV with the entire state: physics, sweep, look, git commits, Julia versions, and copies of the configuration's source files.Reproducing a figure months later.
Look → SaveThe look only: layout, axes, slider positions, camera, labels, exploration options, UI styles.Applying a house style to any simulation.
Simulation → SaveThe physics only: shared and method parameters, active methods, sweep, reference/post-processing functions.Switching between setups (coarse/fine grid, test cases) without touching the look.

Presets are listed under Presets › in the Files tab, with Apply and Edit › (the rows of the preset file). Look → Reset restores the default look, Simulation → Reset the configuration you bound with set_sim_config! (or loaded from a CSV). See Presets for the file format and the API.

Data buttons, number tables and data from outside

  • Data row of the Files tab: Resolution › (the display resolutions), Compute: on/off (the session setting set_compute!: off, Run Simulation and loaded files only show what is stored and list the missing runs) and u − u_ref: on/off (set_error_field!: the pointwise difference to the reference as a field, added when data is loaded, so Run Simulation after switching).
  • Number tables: a name ending in .md or .txt makes Export write the plotted numbers of the 1D subplots (studio_export_data: the points with the local log-log slopes, a Markdown table per subplot or CSV text) instead of a figure; md or txt among the export formats (Settings ›) writes them next to the figure.
  • Data from outside: Load (or a drop) of a plain CSV file with two numeric columns draws it in the 1D and 2D plots as an External Series named after the file (studio_add_series!), in the plotted x variable and the vertical one (the dependent field of a 1D plot, the y variable of a 2D plot, e.g. a curve separating regions of a heatmap): it is hidden while the plot shows other axes. The format: one point per line, its first two numbers, separated by a comma, a semicolon, a tab or spaces (a decimal comma is read with a semicolon or tab, 0,25;2e-3); quotes and a header line are skipped. A file that is neither this nor a studio CSV is reported in the status line. The series are an option page, UI → External Series (points per label, line style, width, marker size; colours and markers continue the methods' lists), get legend entries and are saved with the look (presets, exports). Loading the same file again replaces it; studio_clear_series!() removes them.
